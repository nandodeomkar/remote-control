<objective>
Close the loop. Every plan before this one BUILDS the update path; this one proves it
moves real bytes onto a real phone and a real PC.

At the end of wave 7 the tree contains the whole feature but the mirror's latest is
`v1.5.0` — a release `12-03` built from the end of wave 2, before the Updates screen
existed. Every client would therefore resolve latest as at-or-below installed and
report "up to date" forever (D-26), leaving nothing to tap. This plan publishes
`1.6.0` from the FINISHED tree, brings both clients onto it by hand (the D-01/CONTEXT
"known one-time cost"), publishes `1.6.1` as the thing to update TO, and then runs the
four Manual-Only Verifications from `12-VALIDATION.md` against them.

Purpose: SC4, SC5 and SC7 are claims about a physical phone, a process that exits and
comes back, and a browser holding a file lock. None of them can be demonstrated by a
test suite, and none of them can be demonstrated at all without a release that postdates
the implementation (D-21).
Output: mirror tags `v1.6.0` and `v1.6.1`, and four recorded observations.

**Context cost.** Only Task 1 consumes executor context (one script run and one API
probe). Tasks 2-4 are human checkpoints whose executor cost is reading back what the
owner reports, so the four-task shape stays well inside the plan budget.

**Why not an rc.** `12-VALIDATION.md` originally said "publish an rc release". It cannot
be an rc: per D-20 and 12-01's recorded `-PreRelease` semantics, GitHub's
`releases/latest` EXCLUDES pre-releases and the client version parser rejects
`X.Y.Z-rcN` as unknown, so a pre-release is deliberately never offered to a client
(D-26: an unknown must not trigger an update offer). The update target has to be a
stable tag. `12-VALIDATION.md` is corrected to match.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public mirror -> the PC's installer spawn | This is the one moment in the phase where a downloaded file is executed with the user's privileges |
| public mirror -> the phone's PackageInstaller | A downloaded APK is handed to the system installer |
| phone -> PC server (WebSocket) | `update.apply` crosses it and is what starts both of the above |
| Chrome -> `{app}\extension` on disk | A third-party process holds a lock on files the installer must replace |
