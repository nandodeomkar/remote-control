<objective>
Give the phone its own half of the feed-and-verify story: an HTTP client that resolves
what the latest release is and where the APK lives, and a downloader that streams ~70 MB
to the app cache with progress, hashes it without ever holding it twice in memory, and
deletes it on any failure.

The phone resolves the APK because the phone executes the APK. That is symmetry with
D-14, not an exception to it — the tier that executes a file is the tier that names it.
The phone never names a file for the PC and never receives one from it.

Purpose: SC4's "sha256 verified before install" has to be a Dart-side gate so widget
tests can reach it; moving the digest into Kotlin would put a security check where the
test suite cannot see it.
Output: `crypto` added, `release_feed.dart`, `apk_download.dart`, and tests pinned to
the shared fixtures.
</objective>

Constant `kReleasesApi` =
`https://api.github.com/repos/nandodeomkar/remote-control-releases/releases/latest`
(D-02), and the three asset-name prefixes `RemoteControl-v`,
`RemoteControl-Setup-v`, `RemoteControl-Extension-v`.

Types: `Release { String version; List<ReleaseAsset> assets; }` and
`ReleaseAsset { String name; String url; int sizeBytes; String? sha256; }`, both with
value-equal `operator ==` and `hashCode` so provider state comparisons behave.
`sha256` holds the digest with the `sha256:` prefix already stripped and lowercased;
`null` means the API returned null or omitted it.

Pure function `Release? parseRelease(String body)` — decodes the JSON, strips a leading
`v` from `tag_name`, maps each asset's `name` / `browser_download_url` / `size` /
`digest`, and returns `null` on any malformed input rather than throwing. Ignore every
other field the API returns (D-03: the API is the whole manifest; there is no separate
manifest file to keep in sync).

Pure function `String? stripDigest(String? raw)` — accepts `sha256:` plus exactly 64
hex characters, lowercases, and returns `null` for null, a different algorithm prefix,
a wrong length, or anything malformed.

Pure function `ReleaseAsset? assetWithPrefix(Release r, String prefix)` — the single
asset whose name starts with the prefix, or `null` for zero or more than one match.

Network function `Future<Release?> fetchLatest({HttpClient? client})` — uses
`dart:io HttpClient` with a connection timeout and an overall timeout (10 seconds is
right for a small JSON body), sets a `User-Agent` header, and sends NO `Authorization`
header (D-01 — sending one would reintroduce the token problem the mirror repo exists to
avoid). Returns `null` on any failure. Log distinguishable lines for an HTTP status
failure (including the number, so a 403 rate limit is diagnosable) and a transport
failure, even though both collapse to the same user-facing "couldn't check" (D-22).
Inject the client so tests never touch the network.

Never cache a resolved `browser_download_url`: it redirects to a time-limited signed
CDN URL. Record this in the file doc and re-resolve immediately before each download.

Create `app/remote_control/lib/update/apk_download.dart`.

`Future<String?> downloadApk(ReleaseAsset asset, {required void Function(int received, int total) onProgress, HttpClient? client, Directory? destDir})`:
- Resolve the destination directory from `ApkInstaller.cacheDir()`, falling back to
  `Directory.systemTemp` when the channel is absent (tests, non-Android). Allow
  `destDir` to be injected for tests.
- Delete any stale file at the destination first, then open a write sink.
- Stream the response, writing each chunk and reporting progress. Emit at most one
  progress callback per 1% or per 250 ms so a 70 MB download does not flood the UI —
  the same throttle the server-side progress uses.
- On completion, flush and close the sink BEFORE hashing; a buffered tail would hash
  wrong.
- Return the file path on success; return `null` on any failure.

`Future<String> sha256OfFile(File file)` — `sha256.startChunkedConversion` into an
`AccumulatorSink<Digest>`, fed from `file.openRead()`, returning lowercase hex. Never
read the file into a single list.

`Future<bool> verifyOrDelete(File file, String? expectedHex)` — a null or empty
expected digest is a HARD failure (D-15): delete and return false, never skip
verification. Compare case-insensitively. On mismatch, delete the file and return
false. Document that this gate runs before the file is ever handed to
`ApkInstaller.install`.

Failure discipline: on EVERY failure path — a socket error, a non-200 status, a write
error, a full disk, or a digest mismatch — delete the partial or bad file before
returning (D-23). Map the outcome to the closed error vocabulary the UI renders:
a transport or status failure is `network`, a write or space failure is `disk`, a
digest failure is `checksum`. Never surface an exception message, a path or a URL to
the caller.

Create `app/remote_control/test/update/apk_download_test.dart`, all offline with an
injected client and an injected temp directory: a successful download reports
monotonically increasing progress ending at the total and returns a path; a mid-stream
error deletes the partial file and returns null; `sha256OfFile` matches a precomputed
digest for known bytes; `verifyOrDelete` returns true and leaves the file for a correct
digest; returns false AND removes the file for a wrong digest; and returns false AND
removes the file for a null expected digest.

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-31 | Tampering | the downloaded APK | mitigate | `verifyOrDelete` runs after the sink is flushed and before `ApkInstaller.install` is called; a mismatch or a null expected digest deletes the file and returns false. The digest comes from the TLS-protected feed, never from a local file or a user input |
| T-12-01 | Elevation of Privilege | (context, PC side) | mitigate | Recorded for continuity: the server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). This module is the phone-side mirror of that rule - the phone resolves the APK because the phone executes it, and it never names a file for the PC |
| T-12-32 | Information Disclosure | feed request | mitigate | No `Authorization` header is ever sent (D-01), so no credential can leak to a redirect target or a proxy. Asserted by a grep criterion, not just by review |
| T-12-06 | Information Disclosure | failure reporting | mitigate | Every failure collapses to `network`, `disk` or `checksum` before reaching the caller; exception text, paths and URLs go to the log only. The UI copy map (12-15) never renders a code |
| T-12-33 | Denial of Service | 70 MB in memory | mitigate | Streamed write plus chunked hashing; no `readAsBytes`, asserted by grep. A stalled socket is bounded by an explicit timeout on the client |
| T-12-34 | Denial of Service | disk exhaustion | mitigate | Any write failure deletes the partial file and reports `disk`; a stale file at the destination is removed before the download starts, so a failed attempt cannot accumulate |
| T-12-SC | Tampering | pub.dev install of `crypto` | mitigate | `crypto` 3.0.7 was verified in 12-RESEARCH.md Package Legitimacy Audit against the pub.dev API: publisher `dart.dev` (verified), 160/160 pub points, ~9.9M downloads per 30 days, source `dart-lang/core`, pure Dart with no platform channels or native code. Note the documented false signal: the ecosystem seam supports npm, pypi and crates only, and checking `crypto` against PyPI returns a misleading SUS for an unrelated package - never validate a pub.dev package against PyPI |
</threat_model>
