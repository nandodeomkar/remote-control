<objective>
Turn four independent inputs — the release feed, the phone's own installed version, the
server's `update.status`, and the live `update.progress` stream — into the three row
states the Updates screen renders, plus the Settings badge.

This plan produces no widgets. It produces the state machine the widgets will read, and
it is where the UI-SPEC's row-state matrix becomes an enumerable, value-equal Dart type
that widget tests can drive directly.

Purpose: the row-state matrix is the biggest correctness surface in the phone half of
this phase. Getting it into a tested provider layer before any pixel exists is what
keeps SC3 ("renders every failure state without breaking the screen") checkable.
Output: a connection-service seam, a bare-version provider, and `update_providers.dart`.
</objective>

Create `app/remote_control/lib/update/update_providers.dart` as a Riverpod 3 `Notifier`

Define a sealed/immutable `UpdateRowState` covering EVERY state in the UI-SPEC matrix,
with value equality: `checking`, `upToDate(installed)`, `available(installed, latest, sizeBytes)`,
`downloading(pct)`, `verifying`, `installing`, `restarting`, `failed(code)`,
`couldNotCheck`, `serverDisconnected`, `serverTooOld`, `pcDidNotReturn`,
`extensionNeverConnected`, `extensionNeedsBrowserRestart`, `unknownVersion`.

Define an `UpdatesViewState` holding the three row states, the footer state
(`neverChecked` / `ok(lastCheckedAt)` / `checking` / `failed`) and the badge flag, with a
hand-written `operator ==` and `hashCode`.

Derivation rules, implemented literally from the UI-SPEC binding rules:
1. `available` is NEVER produced for a version at or below installed (D-26). An
   unparseable installed or latest version resolves to `unknownVersion`, never to
   `available`.
2. The Extension row NEVER has an enabled action in any state (D-18). Its `available`
   variant is a distinct display-only case.
3. A feed-fetch failure is SCREEN-scoped: all three rows go to `couldNotCheck`
   simultaneously and the single retry affordance lives in the footer, not in the rows
   (D-22). Row-level retry is reserved for row-scoped apply failures on the App and PC
   rows.
4. `serverTooOld` blanks BOTH the PC and Extension rows with the same state, because a
   1.7 server cannot report `extVersion` through a family it does not know.
5. `busy` is NEVER a row state — swallow it, log it, change nothing on screen (D-11).
6. `downgrade` is NEVER a row state — render it as `failed('installer')` and log the
   real code. An impossible state degrades to a generic honest message, never to one
   that implies the user did something.
7. The App row is NEVER gated by connection state; the PC and Extension rows are
   (`serverDisconnected` when there is no live authed socket).
8. APK success is unobservable: the App row's terminals are `installing`, a fresh launch
   reading `upToDate` from a new `package_info_plus` value, `failed`, and a decline that
   returns the row to `available`. Do NOT persist an installing flag.

Cadence (D-07): expose a `check()` command that fetches the feed and sends
`update.check`, and a launch-time quiet check that runs at most once per 24 hours off
`update_cache` and produces NO visible state change — it must not set the footer to
`checking` and must leave the last-good cached result in place on failure.

Badge (D-06): a provider implementing the badge truth rule exactly — the flag is true
when, and only when, at least one component whose installed version is KNOWN is strictly
behind the CACHED latest version. It never lights on `unknownVersion`, `couldNotCheck`,
`serverDisconnected`, `serverTooOld`, or a stale or absent cache; it reads from
`update_cache` so it is correct offline and before the Updates screen has ever been
opened; and it clears the frame the last out-of-date known component reaches
`upToDate`. There is no dismiss gesture and no "seen" flag.

Commands: `updateApp()` (grant check via `ApkInstaller.canInstall`, then download,
verify, install) and `updatePc(target)` (send `update.apply`). Neither takes anything
but a version string.

Create `app/remote_control/test/update/update_providers_test.dart` driving each state
in the matrix through injected fakes for the feed, the cache, the connection service and
the installer channel. Assert value equality (the same inputs produce an equal state),
assert every binding rule above by name, and assert the badge rule for each of its
never-light cases.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PC server -> phone state | `update.status` and `update.progress` are server-controlled values that drive what the user is told |
| phone state -> user action | This layer decides which buttons exist |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | `updatePc` and `sendUpdateApply` | mitigate | The server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). The phone-side API mirrors that: `sendUpdateApply` takes exactly one `String` with no overload and no options object, so there is nowhere for a locator to be added by a future caller |
| T-12-18 | Tampering | a crafted release tag | mitigate | An unparseable version resolves to `unknownVersion`, never to `available` (D-26), so a tag such as `9.9.9-evil` or `latest` cannot manufacture an Update button |
| T-12-06 | Information Disclosure | error rendering | mitigate | `failed` carries only one of the seven closed D-11 codes, which the copy map turns into a fixed sentence. No code, HTTP status, exception class, path, URL or hash can reach the screen because none of them is representable in the state type |
| T-12-48 | Spoofing | a lying server | accept | A paired, authed server that reports a false `serverVersion` can only misinform the row. It cannot cause the phone to install anything - the APK path resolves its own asset and verifies its own digest, and the PC path is refused server-side by the `stale` and `downgrade` gates |
| T-12-49 | Denial of Service | progress flood into the UI | mitigate | Progress is throttled at the server (about 1% or 250 ms) and the state type is value-equal, so an unchanged tick rebuilds nothing |
| T-12-50 | Tampering | stuck installing state | mitigate | No installing flag is persisted, so a fresh launch after the APK install cannot read one as stuck. Success is inferred from a new `package_info_plus` value |
| T-12-SC | Tampering | pub.dev installs | accept | No dependency added by this plan |
</threat_model>
