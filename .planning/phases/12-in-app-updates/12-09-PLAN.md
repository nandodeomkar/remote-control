<objective>
Build the two pieces that survive the server's own death: the marker file that carries
the outcome of an update across the process swap (D-12), and the detached helper that
sequences wait-then-install-then-relaunch (D-16).

Both exist because of one fact: for Inno's `AppMutex` gate to pass, the server must
exit — and the process that knew whether the install worked is therefore gone before
it can report anything. Disk is the only tier that survives, and a process outside the
server is the only thing that can sequence the swap.

**Correction carried from 12-RESEARCH.md, superseding the design spec's wording:**
`/VERYSILENT` alone does NOT suppress the AppMutex dialog. Inno's check is a
suppressible `MB_OKCANCEL` whose suppression is armed only by `/SUPPRESSMSGBOXES`
combined with a silent switch, and it runs BEFORE the CloseApplications stage. So
`/SUPPRESSMSGBOXES` is mandatory, and the helper's wait-for-PID-exit is load-bearing
rather than defensive — the suppressed default is IDCANCEL, so a still-held mutex
aborts the install outright.

Purpose: a failed install must be diagnosable from the phone. Without the marker it is
indistinguishable from a slow one.
Output: `marker.rs`, `apply.rs`, and a golden-string test over the generated helper.
</objective>

API:
- `write_pending(target: &str)` — writes `{"target": target, "ok": false, "error": "installer"}`
  with `serde_json`. Called BEFORE the helper is spawned, so any way the process dies
  leaves an honest pessimistic record (D-16). A write failure is logged at warn and
  swallowed; it must never abort the update.
- `take_marker() -> Option<LastUpdate>` — reads the file, parses it, DELETES the file,
  and returns the value. Delete on READ, not on report: a phone that never reconnects
  must not leave a permanent marker. `NotFound` returns `None` with no warn and no
  error line. A corrupt file returns `None` and is deleted anyway.
- `truncate_update_log_if_large()` — the RESEARCH Open Question 4 decision, resolved
  here rather than left implicit: the helper appends to `update.log` from a `cmd`
  process that cannot participate in `tracing-appender` rotation, so the server
  truncates the file at startup when it exceeds 64 KiB. Three lines, no rotation
  machinery, unbounded growth prevented.

Tests in a `#[cfg(test)]` module, all against a temp directory injected through a
path parameter or a test-only override so they never touch the real `%APPDATA%`:
`marker_lifecycle` writes pending, takes it, asserts the returned value and asserts the
file is gone; a second `take_marker` returns `None`; an absent marker returns `None`
and produces no error; a corrupt marker returns `None` and the file is removed; the log

Add `pub mod apply;` to `server/server-windows/src/update/mod.rs`.

Create `server/server-windows/src/update/apply.rs` with a `//!` header recording the
one fact the whole design rests on: the server must die for Inno's AppMutex gate to
pass, so only a process outside it can sequence wait, install and relaunch.

Write a PURE function
`helper_script(pid: u32, setup: &Path, installed_exe: &Path, marker: &Path, log: &Path, target: &str) -> String`
producing the `.cmd` text. Requirements, each with its reason in a REM comment:

1. `@echo off` and `setlocal`, then `set` lines for PID, SETUP, EXE, MARKER, LOG and
   TARGET. **Every substituted value is quoted**, and `target` has already been
   validated as `^\d+\.\d+\.\d+$` by the caller — an unvalidated value here is a `cmd`
   injection. Add a debug assertion on the target format inside this function too.
2. A bounded wait loop for the server PID: poll with
   `tasklist /FI "PID eq %PID%" /NH | find "%PID%" >nul` and sleep with
   `ping -n 2 127.0.0.1 >nul`. Use `ping`, NOT `timeout /t` — `timeout` fails when
   stdin is not a console, which a DETACHED_PROCESS child does not have. Cap at 30
   iterations; on timeout append a line to LOG and exit WITHOUT running setup, leaving
   the marker at ok:false and the still-installed old server working.
3. Run the setup with `/VERYSILENT /NORESTART /SUPPRESSMSGBOXES` plus
   `/LOG="%TEMP%\rc-setup.log"` so an installer failure is diagnosable at all.
   `/SUPPRESSMSGBOXES` is mandatory, not optional — see the objective's correction.
4. On a non-zero exit, append a timestamped line to LOG and jump straight to the
   relaunch, leaving the marker at ok:false (D-24). On a zero exit, rewrite the marker
   to `{"target":"<target>","ok":true}` first.
5. Relaunch with `start "" "%EXE%"` unconditionally after the install attempt, because
   `[Run]` carries `skipifsilent` and Setup will not start the app itself.
6. Delete the downloaded setup file, then self-delete with the standard
   `(goto) 2>nul & del "%~f0"` idiom.

Add a `#[cfg(test)]` golden test `helper_script_text` asserting: every placeholder is
substituted (no `__` markers remain); the text contains `/VERYSILENT`, `/NORESTART`,
`/SUPPRESSMSGBOXES`, `tasklist /FI`, `ping -n 2 127.0.0.1` and `start ""`; the text
does NOT contain `timeout /t`; the ok:true rewrite appears exactly once and only on the
zero-exit path; and a target containing a quote, an ampersand or a path separator is
rejected by the debug assertion rather than interpolated.
  </action>

`fn installed_exe() -> PathBuf` — the directory of `std::env::current_exe()` joined
with the fixed installed exe name `RemoteControl.exe`. Document the reasoning: the
running process IS `{app}\RemoteControl.exe` because the installer renames the build
output via `DestName`, and resolving from the current exe's PARENT rather than reusing
the current exe path directly keeps the relaunch correct if the exe is ever renamed.
Degrade rather than panic if `current_exe` fails.

`fn spawn_helper(script: &Path) -> std::io::Result<()>` — runs
`cmd.exe /c <script>` with `creation_flags(DETACHED_PROCESS | CREATE_NO_WINDOW)`, all
three stdio handles set to null (an inherited handle would keep this process's pipes
alive and can block the child's writes), and `.spawn()` — deliberately NOT `.wait()`,
because this process is about to exit and an unwaited `Child` has no `Drop` impl to
kill it.

`fn begin_apply(target: &str, setup_path: &Path) -> Result<(), UpdateError>` — the
sequencing entry point, called only after the download has been verified:
1. `marker::write_pending(target)`.
2. Write the helper script into `%TEMP%` at a per-PID filename such as
   `rc-update-<pid>.cmd`.
3. `spawn_helper`.
4. Return `Ok(())`. The CALLER is responsible for the process exit; document that
   `begin_apply` does not call `exit` itself so the update thread can publish a final
   `restarting` progress stage first, giving the phone a chance to render it before the
   socket drops.

Map every failure to `UpdateError::Installer` and log the underlying error, never
returning it — the closed D-11 vocabulary is what reaches the wire.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verified `%TEMP%` file -> executed installer | The moment unverified-until-now bytes become a running process with the user's privileges |
| generated `.cmd` text -> `cmd.exe` | Every substituted value is executed as a command line |
| marker file -> next server process | State crosses a process boundary through the filesystem |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | `begin_apply` and the generated helper | mitigate | The server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). `begin_apply` receives a validated version string and a server-chosen `%TEMP%` path; no wire value reaches the setup path, the exe path or the marker path |
| T-12-26 | Elevation of Privilege | `target` interpolated into the `.cmd` | mitigate | `target` is validated as `^\d+\.\d+\.\d+$` before any use and again debug-asserted inside `helper_script`; every substituted value is quoted in the generated text. A test proves a target carrying a quote and an ampersand cannot inject a command |
| T-12-27 | Tampering | unverified bytes executed | mitigate | `begin_apply` is called only after `verify_or_delete` succeeded (12-06); a mismatch deletes the file and never reaches this module. The helper is written after the pessimistic marker so an interrupted sequence is still recorded honestly |
| T-12-28 | Denial of Service | a server that refuses to die | mitigate | The helper's PID wait is bounded at ~30 iterations; on timeout it logs and exits WITHOUT running setup, leaving the still-installed old server working rather than firing an install into a held mutex |
| T-12-29 | Tampering | AppMutex dialog under a "silent" install | mitigate | `/SUPPRESSMSGBOXES` is passed alongside `/VERYSILENT`, so a mutex still held despite the PID wait aborts to a decodable non-zero exit instead of parking a modal dialog on the user's desktop forever |
| T-12-06 | Information Disclosure | error reporting | mitigate | Every failure in this module collapses to `UpdateError::Installer`; paths and OS error strings go to `tracing` and `update.log` only, never to the wire |
| T-12-30 | Tampering | helper script in `%TEMP%` | accept | A local process able to rewrite `%TEMP%` before the detached spawn already owns the machine, which is the same accepted residual SPEC Sec 12 records for the loopback extension leg. The script is per-PID-named and self-deletes |
| T-12-SC | Tampering | cargo installs | accept | No new dependency; `dirs`, `serde_json` and `tracing` are already in the tree |
</threat_model>
