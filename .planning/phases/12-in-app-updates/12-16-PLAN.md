<objective>
Close the extension leg: the server notices that the extension is running an older
version than itself, nudges it exactly once, and the extension re-reads its files from
disk without anyone opening `chrome://extensions`.

**This plan opens with a blocking human action, and that is deliberate.** 12-RESEARCH.md
raised a risk the design spec did not anticipate: if Chrome holds a write lock on
`{app}\extension\*`, Inno's file-replace failure raises an Abort/Retry/Ignore whose
SUPPRESSED DEFAULT IS ABORT — which aborts the ENTIRE server install, not just the
extension. That would turn "the browser happened to be open" into a total PC-update
failure, and the browser being open is the common case, not an edge case. Whether the
lock is real is a five-minute observation on a real machine, and it decides how the
`.iss` entry must be written. Do not treat this slice as low-risk glue.

Purpose: SC7 — the extension is running the new version after a PC update without the
user touching `chrome://extensions`, and a blocked overwrite degrades to a message
rather than a loop or a failed install.
Output: one `ExtCmd` variant, one guard, one extension arm, one hardened installer line.
</objective>

Two unknowns must be settled by observation on a real machine before the rest of this
plan is written. Both are one procedure. It needs a human because loading an unpacked
extension requires interacting with `chrome://extensions`, which an agent cannot do.

**Procedure (about five minutes):**

1. Have the current release installed, so `{app}\extension` exists on disk.
2. Open Chrome (or Edge), go to `chrome://extensions`, enable Developer mode, and
   Load unpacked from the installed `{app}\extension` directory. Confirm the extension
   loads and connects (the phone's browser screen shows tabs).
3. Leave the browser OPEN.
4. From an elevated-or-not terminal matching how the installer normally runs, execute
   the setup exe over the existing install with exactly:
   `RemoteControl-Setup-vX.Y.Z.exe /VERYSILENT /NORESTART /SUPPRESSMSGBOXES /LOG="%TEMP%\t.log"`
5. Immediately afterwards, record `%ERRORLEVEL%`.
6. Search `%TEMP%\t.log` for `ErrorReplacingExistingFile` and for any Abort/Retry/Ignore
   entry.
7. Separately, confirm the server relaunches and note whether the extension reconnects
   and what `extVersion` its `ext.hello` reports (watch the server log).

**Report back three facts:**

- **A.** The setup's exit code, and whether the log contains a file-replace failure.
- **B.** Whether the server exe itself was replaced (check its version in
  Properties, or the version the tray reports after relaunch).
- **C.** Whether the extension's `ext.hello` reports the NEW version after a
  `chrome.runtime.reload()`-equivalent, or still the old one.

**Why each matters:**
- If A shows a file-replace failure AND B shows the server exe was NOT replaced, the
  Pattern 5 `restartreplace` mitigation is MANDATORY and Task 3 applies it.
- If A shows a failure but B shows the server was still replaced, the mitigation is
  advisable but not load-bearing.
- If A is clean, the mitigation is cheap insurance and Task 3 still applies it, but the
  risk note in the summary changes from "confirmed" to "not reproduced".
- C decides whether SC7's "without touching chrome://extensions" is achievable at all,
  or whether the D-18 fallback copy ("restart your browser") is the normal outcome
  rather than the exception. Either way the feature degrades rather than breaks, but the
  plan must not CLAIM SC7 is met until C is observed.

Do NOT skip this and assume an answer. Both A and C are marked `[ASSUMED]` in the
research and neither is documented anywhere authoritative.

  <action>
Add `Reload` to the `ExtCmd` enum with a doc comment: `ext.reload` — srv-to-ext only,
empty payload; the extension calls `chrome.runtime.reload()` and re-reads its files
from disk. Add the matching dispatch arm in `run_ext`'s command loop, serialising it as
`{"t":"ext.reload","p":{}}` in the same shape the other commands use.

`run_ext` needs the server's own version to compare against. Add a
`server_version: String` parameter and pass `env!("CARGO_PKG_VERSION").to_string()` from
`server-windows/src/main.rs` at the spawn site — the version must come from the
`server-windows` package, because `server-core`'s own `CARGO_PKG_VERSION` is the library
crate's version and is not what ships (D-05).

Add the guard as a local `Option<String>` inside `run_ext`, named for what it holds: the
target version a reload has already been attempted for, this process run.

On `ext.hello`, after publishing `ExtInfo` (12-12's behaviour, unchanged):
- if the reported `extVersion` is `Some(v)` and `v != server_version`,
- and the guard is not already `Some(server_version)`,
- then set the guard to `Some(server_version.clone())` and send `ExtCmd::Reload` to the
  extension.

Never reset the guard during a process run. A server restart is the only reset, which is
exactly the intent: because `chrome.runtime.reload()` makes the extension reconnect and
send a fresh `ext.hello`, a second hello carrying the SAME stale version finds the guard
already set and sends nothing. That is what makes a Chrome-blocked overwrite degrade to
a message instead of a loop.

An absent `extVersion` never triggers a reload — unknown is not "different".

Add tests to `ext_relay.rs`: a hello with a differing version sends exactly one reload; a
SECOND hello with the same differing version sends none (the loop assertion, and the
single most important test in this plan); a hello with a MATCHING version sends none; a
hello with no `extVersion` sends none; and after a reload the guard survives a session
end and reconnect within the same process run.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server -> extension (loopback 127.0.0.1) | `ext.reload` crosses here; any local process could open this socket |
| Inno installer -> `{app}\extension` | A file replace that fails can abort an install that had nothing to do with the extension |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | (context, apply path) | mitigate | Recorded for continuity because this plan touches the installer entry the apply path executes: the server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). Nothing in `ext.reload` widens that - it is srv-to-ext only, carries an empty payload, and the extension never sends it |
| T-12-55 | Spoofing | a local process forging `ext.hello` with a stale version | accept | Already-accepted residual (SPEC Sec 15): a local process able to open a loopback socket owns the machine. The bounded consequence here is at most ONE `chrome.runtime.reload()` per process run, because the in-memory guard is keyed on the target version and is never reset |
| T-12-56 | Denial of Service | reload loop | mitigate | The once-per-target-version guard is the loop breaker, and its single most important test asserts that two consecutive stale `ext.hello` frames produce exactly one reload. Without it, a Chrome-blocked overwrite would make the extension reload forever |
| T-12-57 | Denial of Service | a locked extension file aborting the whole PC install | mitigate | `restartreplace` on the extension `[Files]` entry degrades a locked file to a next-boot replacement instead of an Abort that takes the server exe with it. The server exe entry stays listed first so the critical artifact lands before the risky one. Settled by observation in Task 1, not assumed |
| T-12-58 | Tampering | `_metadata` written into the extension directory by Chrome | accept | `recursesubdirs` copies into the directory without pruning, so Chrome's own folder survives harmlessly, and `[UninstallDelete]` removes it on uninstall. No clean-directory step is added, deliberately - one would fight Chrome |
| T-12-SC | Tampering | npm/pip/cargo installs | accept | No dependency added; the extension has no build step and no package manager |
</threat_model>
