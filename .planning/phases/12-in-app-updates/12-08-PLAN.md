<objective>
Build the Android side of the APK self-update (D-19): a hand-written MethodChannel
mirroring `platform/multicast_lock.dart`, a `PackageInstaller` session in
`MainActivity.kt`, and a `BroadcastReceiver` that launches the system's own
confirmation dialog.

No UI and no download logic here — this plan produces the capability, and 12-15 wires
it to a button. The plan sits behind 12-01 for sequencing only (D-21: release tooling
lands before client-side work); there is no code dependency.

Purpose: package installation is the OS's authority. The app stages bytes and commits;
Android decides. Doing this through the legacy `ACTION_INSTALL_PACKAGE` intent instead
would give no outcome callback at all, which is exactly what D-19's "declined returns
the row to available" requires.
Output: `apk_installer.dart`, two Kotlin files, one manifest permission and one
receiver entry.
</objective>

`MethodChannel('remote_control/installer')` with four methods:
- `Future<bool> canInstall()` — returns whether the install-unknown-apps grant is held.

  as if the grant exists and the explainer sheet never opens spuriously.

  package. No-op on `MissingPluginException`.

  path, so `apk_download.dart` (12-10) has somewhere to stream 70 MB without adding a
  `path_provider` dependency. Returns `null` on `MissingPluginException`, and the
  caller falls back to `Directory.systemTemp` in tests. Document that this method
  exists specifically to keep the phase's new-dependency surface at exactly one Dart
  package (`crypto`), consistent with the project choosing `RawDatagramSocket` over a
  wrapper package for the beacon.
- `Future<void> install(String apkPath)` — hands an already-downloaded, already-verified
  file to the platform. No-op on `MissingPluginException`. Document that verification
  happens in Dart BEFORE this call and that the platform side never verifies: keeping
  the security gate in testable Dart is deliberate, and the channel does only what only
  it can do.

Add a `Stream` or callback seam for install outcomes, delivered from the platform via
an `EventChannel` or a `setMethodCallHandler` reverse call — choose one and document
it. The outcomes the caller can observe are `pendingUserAction`, `declined` and
`failure` (with a status code). Add a file-top doc comment recording why SUCCESS is NOT
in that list: replacing the APK terminates this app's process, so the success broadcast
is delivered to a process being torn down. Success is confirmed by the app simply
relaunching at a new `package_info_plus` version, exactly the way the PC update is
confirmed by reconnecting. Never persist an "installing" flag that a fresh launch would
read as stuck.

`SessionParams(MODE_FULL_INSTALL)`, then the exact sequence `createSession`,

stream, close, and `commit(pendingIntent.intentSender)`. Build the `PendingIntent` with

declares neither mutability flag. Use the session id as the request code so concurrent
sessions cannot collide.

Wrap the session work so any exception is reported back through `result.error` with a
short code rather than crashing the activity, and close the session on the failure
path.

Add a comment recording that `commit()` does NOT show a dialog itself: it first calls

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app cache file -> Android package installer | A file becomes an installed application here |
| broadcast receiver -> other apps | An exported receiver would let any app feed it fake install statuses |
| app -> system settings | The grant intent leaves the app's control |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-21 | Spoofing | `InstallResultReceiver` | mitigate | Declared `android:exported="false"` and targeted by an explicit-component `PendingIntent`, so only the system's `PackageInstaller` callback can reach it. A forged status from another app cannot make the row report success or launch an arbitrary confirmation intent |
| T-12-22 | Elevation of Privilege | `PendingIntent` mutability | mitigate | `FLAG_MUTABLE` is required because the system fills in the status extras, but the intent names an explicit, non-exported component in this package, so mutability grants no cross-app capability. `FLAG_UPDATE_CURRENT` plus the session id as request code prevents session cross-talk |
| T-12-23 | Tampering | the APK handed to `install` | mitigate | Verification is a Dart-side gate that runs before this channel is called (12-10). Keeping sha256 in testable Dart rather than in Kotlin is deliberate: a security gate inside platform code is unreachable by widget tests. The platform side never re-verifies and never fetches |
| T-12-24 | Tampering | signature or downgrade attack | mitigate | Android itself refuses a differently signed APK or a lower `versionCode`; the receiver surfaces `STATUS_FAILURE_CONFLICT` as an actionable failure. `tools/release.ps1` refuses to build without the release keystore, so a debug-signed artifact never reaches a user |
| T-12-06 | Information Disclosure | `EXTRA_STATUS_MESSAGE` | mitigate | Logged only. Never forwarded to Dart or rendered - it is device-specific and can contain paths |
| T-12-25 | Denial of Service | stuck installing state | mitigate | Success is deliberately unobservable, so no "installing" flag is persisted and a fresh launch can never read one as stuck (RESEARCH Pitfall 7) |
| T-12-01 | Elevation of Privilege | (context) | mitigate | Recorded for continuity: on the PC side, the server resolves every asset URL and hash itself from a compiled-in repo constant and never accepts, derives, or is influenced by a target supplied over the wire (D-14). The phone-side symmetry is that the phone resolves the APK because the phone executes the APK - it never names a file for another tier |
| T-12-SC | Tampering | pub.dev / gradle installs | accept | No Dart package and no Gradle dependency is added by this plan; `PackageInstaller` is an OS API |
</threat_model>
