`update.check` / `update.status` / `update.apply` / `update.progress` / `ext.reload`
(D-09), the closed `stage` (D-10) and `error` (D-11) vocabularies, the D-14

`protocol/fixtures/beacon/01-valid.json`. Those flip atomically with

put the spec ahead of the code for five waves.

Purpose: both decoders are pinned to the same bytes, as every other message family in

Sec 7: add five rows in the existing registry format.
`update.check` C-to-S, payload `{}`, no optional fields.
`update.status` S-to-C, required `serverVersion` (string) and `extConnected` (bool),
optional `extVersion` (string, absent when the extension has never connected) and
`lastUpdate` (object).
`update.apply` C-to-S, required `target` (string, `X.Y.Z`) and no other field, now or
later.
`update.progress` S-to-C, required `stage` (string), optional `pct` (integer 0-100),
`version` (string), `error` (string).
`ext.reload` srv-to-ext, payload `{}`, cross-referencing Sec 15.

Under those rows add three short subsections:
- stage vocabulary (D-10): the closed list `checking`, `downloading`, `verifying`,
  `installing`, `restarting`, `uptodate`, `failed`. State that `pct` accompanies
  `downloading` ONLY, and that `uptodate` and `failed` are terminal.
- error vocabulary (D-11): the closed list `network`, `checksum`, `disk`, `installer`,
  `downgrade`, `stale`, `busy`. State that it is never free text, never a path, never
  an HTTP status and never an exception name.
- `lastUpdate` (D-12): `{target: string, ok: bool, error?: string}`, reporting the
  outcome of the PREVIOUS attempt, read from a startup marker and present only when a
  marker exists. Record why it exists: the process that would have reported the
  failure had already exited to let the installer replace it.

Sec 11: add `update.check` and `update.apply` to the executor-bound list, and note
explicitly that `update.check` is executor-bound DESPITE being a read - unlike
`bm.list`, `apps.list` and `clip.get` - because it reports state about a machine that
is about to be replaced (D-13).

Sec 10: add a sentence recording that a 1.7 server answers any `update.*` type with
`err {code:"unknownType"}` and keeps the session alive, and that a 1.8 client renders
that as "server too old to update itself" (D-13, SC8).

Sec 12: add the D-14 paragraph. `update.apply` grants the client NO locator authority.
The server resolves the asset URL and its sha256 itself from a compiled-in repo
constant and refuses any URL, filename, asset index or hash supplied, implied or
influenced by the wire. Record why: a wire-supplied locator would convert a paired
phone - or anything that obtained a token - into arbitrary code execution on the PC.
State that this is the strongest constraint in the protocol and must not be relaxed
for convenience. Also record, in the accepted-residual style Sec 12 already uses, that
a compromised owner-controlled mirror repo is equivalent to a compromised source repo,
and that no update manifest file is published because the releases API already carries
tag, asset names and per-asset digests (D-03).

Sec 15: add `ext.reload` as a srv-to-ext command with an empty payload, note that the
extension never sends it, and record the D-18 guard - the server sends it at most once
per target version per process run, and a version that still disagrees after a reload
produces no second attempt.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| phone -> PC server (WebSocket) | The `update.*` family crosses it; this plan defines what may cross |
| PC server -> extension (loopback) | `ext.reload` crosses it |
| GitHub releases API -> both clients | Untrusted-until-verified JSON; this plan pins its shape |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | `update.apply` payload shape | mitigate | The fixture and the SPEC row define `update.apply` as carrying exactly one field, `target`. The server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). Fixture `04-update-apply.json` is the machine-checkable form of that rule; SPEC Sec 12 is the human-readable one |
| T-12-06 | Information Disclosure | `update.progress.error` | mitigate | D-11's closed seven-value vocabulary is written into SPEC as a closed list precisely so a path, a URL, an HTTP status or an exception string can never reach the phone |
| T-12-07 | Tampering | release feed digest | mitigate | Fixture `12-releases-latest-null-digest.json` makes "absent digest is a hard `checksum` refusal" an executable contract rather than a code comment |
| T-12-08 | Spoofing | protocol forward compatibility | accept | A 1.7 server answering `unknownType` keeps the session alive by design (SPEC Sec 10). Documented, not changed |
| T-12-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing. The phase's two new dependencies are audited in 12-RESEARCH.md Package Legitimacy Audit with verdict OK and are introduced in 12-06 and 12-10 |
</threat_model>
