<objective>
Build the three pure pieces the phone's update surface stands on: version comparison
(D-26), the 24-hour check cache (D-07), and the two formatters the UI copy contract
requires (D-08).

All three are I/O-free or prefs-only and therefore fully unit-testable. Version
comparison is pinned to `protocol/fixtures/update/10-version-compare.json` — the same
file `server-core`'s test loads — because the two sides disagreeing about what "newer"
means would show up as the phone offering an update the server then refuses as
`stale`.

Purpose: get the decisions that determine *whether anything is offered at all* into
tested pure functions before any screen or network code exists.
Output: `lib/update/{version,update_cache,update_format}.dart` and their tests.
</objective>

Create `app/remote_control/lib/update/version.dart` with a file-top doc comment stating
that it is pure with no I/O, and that an unparseable version is UNKNOWN and must never
produce an update offer.

`SemVer implements Comparable<SemVer>` with `final int major, minor, patch`, a `const`
constructor, and `static SemVer? tryParse(String s)`. `tryParse` accepts an optional
leading `v` and exactly three non-negative integer components, matching
`^v?(\d+)\.(\d+)\.(\d+)$` after trimming. It returns `null` for `1.4`, for
`1.4.0-rc1`, for the empty string, for `latest`, and for any component that does not
fit an `int` — parse with `int.tryParse` and return `null` on overflow rather than
throwing. `compareTo` compares major, then minor, then patch as integers, never as
strings: `1.10.0` is newer than `1.9.0`, and a float or lexical comparison gets that
backwards.

Add `bool isNewer({required String candidate, required String installed})` — the only
question the UI asks. If either side fails to parse it returns `false`. Add
`String? normalize(String s)` returning the canonical `X.Y.Z` form with any leading `v`
stripped, or `null` when unparseable, for use by the row copy (the UI renders installed
and latest verbatim with a leading `v` stripped, never reformatted or zero-padded).

Add a doc comment recording the pre-release consequence: `X.Y.Z-rcN` returns `null`, so
a pre-release is never offered to a client. This is deliberate and consistent with
"update channels other than latest-stable" being out of scope; GitHub's
`releases/latest` already excludes pre-releases, making the client-side rejection a
second belt rather than the primary mechanism.

Create `app/remote_control/test/update/version_test.dart`. It loads
`protocol/fixtures/update/10-version-compare.json` from the repo (resolve the path
relative to the test file, the way other tests in this project reach `protocol/`) and
asserts every case in `cases`: `newer`, `older`, `same`, and `unknown` where `unknown`
means neither `isNewer(a, b)` nor `isNewer(b, a)` is true. Add direct unit cases for
`normalize` and for the overflow input.

API:
- `Future<UpdateCacheState> load()` — a corrupt, missing or type-mismatched value
  degrades to the never-checked default. It must never throw and never log an error
  for the absent case; an empty cache is the normal first run.
- `Future<void> save(UpdateCacheState)` — fire-and-forget, matching the seam.
- `bool isStale(UpdateCacheState s, {required DateTime now})` — true when there is no
  last check, or when `now` minus the last check is at least 24 hours. `now` is
  injected so the TTL is testable without waiting or mocking the clock.

Add a file-top doc comment recording two rules: this data is NON-SECRET and therefore
lives in `shared_preferences` and never in secure storage (Keystore operations are slow
and can throw after OS updates); and a background check that fails must leave the last
good cached result in place and produce no visible change, because a stale or failed
background check must never interrupt the user (D-07, D-22).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release feed -> phone version logic | A tag string from the internet decides whether an update is offered |
| shared_preferences -> app | Locally stored, non-secret, and readable by anything with device access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-18 | Tampering | version comparison | mitigate | Integer tuple comparison, never lexical and never float. An unparseable tag yields `unknown` and `isNewer` returns false, so a crafted tag such as `latest` or `9.9.9-evil` cannot manufacture an offer (D-26 and CONTEXT specifics) |
| T-12-19 | Tampering | the 24h cache | accept | `shared_preferences` is not a security boundary. The worst a tampered cache achieves is a stale "last checked" line or an early re-check; it cannot cause a download, because nothing downloads until a button is tapped (D-07) and the server re-resolves the feed itself before any apply (D-15 `stale`) |
| T-12-20 | Information Disclosure | cached values | mitigate | Only a timestamp and a public version string are cached. No token, no PIN, no device identity - which is also why `shared_preferences` and not secure storage is correct here |
| T-12-01 | Elevation of Privilege | (context) | mitigate | Recorded for continuity: whatever this module decides to offer, the server still resolves every asset URL and hash itself from a compiled-in repo constant and never accepts, derives, or is influenced by a target supplied over the wire (D-14). The phone's comparison is a UI affordance, not an authority |
| T-12-SC | Tampering | pub.dev installs | accept | This plan adds no dependency; `shared_preferences` is already in the tree |
</threat_model>
