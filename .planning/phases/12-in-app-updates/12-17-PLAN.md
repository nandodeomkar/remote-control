<objective>
Give the PC its own update path (D-06). A broken, unpaired or absent phone must not leave
the Windows machine with no way to update itself, and the whole point of this phase is
to delete the hand-download procedure — so the fallback must not be "open a browser and
download a file", which is exactly that procedure.

**Discretion resolved by the approved UI contract:** the PC settings section performs its
OWN feed check. The server already owns `feed.rs`, `download.rs` and `apply.rs` for the
phone-driven path (D-14 requires it to resolve its own asset regardless), so the local
check reuses that seam and adds no new resolution logic and no new I/O.

**This is a different design system from the phone.** It renders in egui with
`server-windows/src/shell/style.rs` tokens; the PC accent is `#38BDF8`, not the phone's
`#4C8DFF`. Never import, copy or approximate a `tokens.dart` value here. The two
surfaces share a copy vocabulary and nothing else.

Purpose: one machine, one truth — both surfaces read the same progress watch, so they
cannot disagree about what is happening.
Output: an `UPDATES` section in the settings window and the plumbing that feeds it.
</objective>

has one) — then `ui.add_space(12.0)`, then `field_label(ui, "Version", None)`, then
`ui.add_space(7.0)`, then the version literal rendered with `style::mono(14.0)` in

The status line uses `style::sg(12.0)` with the colour chosen by state: `style::MUTED`

same treatment the shipped `Restart to apply` hint uses); `style::RED` on failure (the
same treatment the shipped `Not a valid port (1-65535)` line uses).

Status copy is IDENTICAL to the phone's sentences, quoted from the UI-SPEC copy table
rather than re-worded: `Up to date · {version}`, `{installed} → {latest} · {size}`,
`Downloading… {pct}%`, `Checking the download…`, `Installing…`, and the same seven-code
error map. Two surfaces describing one failure with different words is the single most
confusing outcome available to this phase.

Progress is a TEXT stage line only. Do NOT add a progress-bar widget: the window has no

Read the progress watch each frame with `borrow()` and map the current stage to the
status line. Skip the empty-stage sentinel (it means nothing has happened yet) and render
the never-checked copy instead.

The section renders no phone row and no extension row. It is a fallback for THIS machine,
not a second control centre.

Add a unit test over the pure stage-to-copy mapping function (extract it, following the

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local user at the settings window -> update path | A second trigger for the same install path |
| update thread -> settings window | Server-produced state rendered locally |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | the `Update now` button | mitigate | The server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). This surface is bound by the same rule: the button sends `UpdateCmd::Apply(latest)` where `latest` is the version the SERVER resolved during its own feed check. There is no text field, no path picker and no way for a human at the window to name a file or a URL. The refusal ladder still runs on every apply, from this trigger as from the phone's |
| T-12-59 | Elevation of Privilege | a local user at the settings window | accept | Anyone at the machine's desktop can already run an installer by hand. This button gives no capability that user did not have, and it removes the SmartScreen-prone manual download path that D-01 and D-16 exist to eliminate |
| T-12-06 | Information Disclosure | the status line | mitigate | Copy comes from the same closed seven-code map the phone uses. No path, URL, HTTP status or exception text is renderable, because the mapping function accepts only a stage and an error code |
| T-12-60 | Denial of Service | concurrent applies from two surfaces | mitigate | Both buttons are disabled while the shared busy flag is set, and the executor's compare-and-swap refuses a second apply regardless. The local surface therefore cannot produce a `busy` refusal it would have to explain |
| T-12-61 | Tampering | design-system cross-contamination | mitigate | A grep criterion asserts no phone token, no `kAccent` and no `#4C8DFF` literal appears in this file. The two surfaces are deliberately separate and must not converge by accident |
| T-12-SC | Tampering | cargo installs | accept | No new dependency in this plan |
</threat_model>
