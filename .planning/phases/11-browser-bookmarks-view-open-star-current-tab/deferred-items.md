# Deferred items — phase 11

Out-of-scope discoveries logged during execution. Not fixed here.

| 1 | 11-05 task 3 | `extension/background.js` caps GROUP titles with `(g.title \|\| "").slice(0, MAX_GROUP_TITLE)`. Like the bookmark title cap, this slices on UTF-16 code units and can leave a lone surrogate when an emoji straddles char 32 — `JSON.stringify` then emits a bare `\ud83d`, which serde_json rejects as a hard decode error. 11-05 fixed its OWN new title cap (`capBmTitle`) but left the shipped group cap untouched. | Pre-existing shipped code on the `tabs.state` path, not caused by 11-05's changes (SCOPE BOUNDARY). Lower blast radius than the bookmark case: `groups` is parsed LENIENTLY server-side (11-02 decision) whereas `bm.state` nodes are strict, and a group title is far less likely than a bookmark title to be emoji-decorated at exactly the cap. Fix is one line: route the group title through the same lone-surrogate trim. |
| 2 | 11-11 task 3 | Press-and-HOLD on a tab-row star for >100 ms also fires the row's `onTapDown` → `tabs.activate`. Flutter's `BaseTapGestureRecognizer` calls `handleTapDown` on deadline expiry (`kPressTimeout`), not only on winning the arena, so the outer row recognizer reports a down even though the nested star recognizer wins the tap. An instant tap (and therefore the A6 test, which sends down+up with no time between) is unaffected. | Not caused by this plan: it is a property of the row's LOCKED tap-down activate, which the plan explicitly forbids restructuring ("the tap-down activate … keeps its exact current behaviour"). Blast radius is a benign tab switch that self-heals on the next `tabs.changed` — no destructive action and no data loss; the star still stars exactly once. A fix means moving row activation to `onTap` or wrapping the star in a `GestureDetector` that claims the arena eagerly, both of which change the shipped press-down feel and belong in their own change. |
| 3 | 11-12 task 2 (on-device UAT) | **Truncation copy is functionally correct but reads as unintuitive.** `kBmTruncatedSnapshot` = `'Showing the first 500 bookmarks.'` (`bookmarks_section.dart:46`) renders as a muted line at the top of the region, and `kBmTruncatedFolder` = `"Some bookmarks here aren't shown."` below the rows of a clipped folder. On device the owner confirmed the snapshot line DOES appear and is accurate — the mechanism works — but judged the presentation unintuitive: a muted top-of-region line does not connect, for a user browsing a deep folder, to "the item you are looking for may simply be absent". Worth noting the copy is now *production* behaviour, not an edge case: the owner's real collection is 538 API-visible nodes against `MAX_BM_NODES` 500, so ~38 nodes are dropped on every snapshot and this line is always on screen. Candidate directions (none decided): make the count concrete/relative ("38 of 538 not shown"), attach the signal to the folder the user is actually in rather than only the region top, or reconsider whether 500 is the right cap given the frame had 19.5 KB of headroom (37,845 B of 57,344 B — see the A3 finding that `MAX_BM_NODES`, not `MAX_FRAME_BYTES`, is the binding constraint). | UX/copy judgement raised during UAT, not a defect — the shipped behaviour matches 11-09's design contract and every automated test. Changing wording, layout, or the node cap is a design decision outside plan 11-12, whose scope is docs + UAT only. Owner explicitly said "mark as open problem and keep for later to solve". A cap change in particular has protocol-budget consequences (raising `MAX_BM_NODES` past ~750 would newly activate the byte-trim loop that currently never runs) and needs its own plan. |
| 4 | 11-13 task 4 (UAT-8 re-run) | **The 100ms press flash is imperceptible on bookmark LINK rows.** Owner, during B4: "no flash on links … one very fast flash on drilling just one level into the bookmarks bar." The flash sets border, glyph and title to `kAccent` for 100ms (~6 frames) and then relaxes. On a folder it is now visible, because the drill-in waits for release and the row stays put during the press. On a link nothing else on the phone changes — the opened tab appears on the PC — so the 100ms accent is easy to miss entirely, and the owner reports seeing none. Candidate directions (none decided): lengthen the relax for link rows, or add a distinct non-visual acknowledgement now that the haptic rides release. Note the folder-bar BACK control is deliberately excluded — it is a separate `InkWell` with `onTap: onBack` and zero `_pressed` references, and has never flashed. | **Explicitly NOT caused by plan 11-13, and verified so** — the flash fires from `onTapDown` both before and after the fix, and on a quick tap the tap recognizer wins the arena at pointer-UP so `onTapDown` and `onTap` land in the same frame either way (pre-fix `_fire()` did the action and then `setState(_pressed = true)` from that same callback). The trigger point is byte-identical, so link-row flash behaviour is unchanged by this plan. Pre-existing perceptual issue, surfaced only because B4 asked the owner to look closely at press feedback for the first time. Changing flash duration is a motion-budget change against 11-UI-SPEC § Motion Budgets and needs its own plan. |
