<objective>
Close UAT-8 / Failure B: make D-14's empty-folder delete and D-13's link delete reachable by a real
gesture, by splitting the visual press flash from the side-effectful action on `_BmRow`.

Purpose: `_BmRow` wires the accent flash, the drill-in/open action and the delete confirm onto ONE
`InkWell`, with the action on `onTapDown`. Flutter's `BaseTapGestureRecognizer.didExceedDeadline()`
calls `_checkDown()`, so `onTapDown` fires at `kPressTimeout` (100ms) whether or not the tap won the
arena, while `LongPressGestureRecognizer` sets `deadline: kLongPressTimeout` (500ms) and only then
calls `resolve(GestureDisposition.accepted)`. Every long press therefore runs the tap-down action
400ms before the long press can resolve. On a FOLDER that action replaces the list, so the pressed
row is gone and D-14's delete is unreachable by any gesture (observed on device with `count == 0`,
where `isDeletable` is true and `onLongPress` IS wired). On a LINK the row survives, so the delete
lands — but only after `bm.open` has already fired, meaning deleting a bookmark force-opens it in a
PC tab first. Both observed on real hardware 2026-07-30 (Xiaomi 25080RABDI + Comet 150.0.7871.115),
recorded in `11-UAT.md` § Failure B.

This plan also fixes the ROOT CAUSE of the bug, which is not the code: `11-UI-SPEC.md`'s Interaction
/ Gesture Map specifies `tap-down: drill in + flash + haptic` AND `long-press: confirm → delete` on
the same folder row. Those two are mutually exclusive by construction. Plan 11-09 implemented the
spec faithfully. Unless the spec is amended, a future executor will faithfully re-implement the same
defect.

Output: a `_flash()` / `_activate()` split on `_BmRowState`, an amended `kBmDeleteHint`, a
regression group that pumps a REAL timed press at both the section and the screen layer, the
corrected gesture map with the deliberate `_BmRow` vs `_TabRow` divergence written down as a rule,
and an on-device re-run of UAT-8.
</objective>
