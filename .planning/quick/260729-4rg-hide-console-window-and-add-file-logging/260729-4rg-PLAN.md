<objective>
Stop the server from opening a console window when launched from the Start
Menu, desktop icon, or autostart entry.

Problem: the binary is built as a console-subsystem exe, so every launch pops a
terminal alongside the tray icon. Now that the installer gives the app three
launch points, that window is in the owner's face constantly.

The attribute that hides it also silences stdout, and stdout is currently the
ONLY logging sink (`main.rs:53` — `tracing_subscriber::fmt()` with no writer
override, and no `tracing-appender` dependency). Hiding the console without a
file sink would trade a cosmetic annoyance for zero diagnostics. So this task
is both halves: hide the window, and give the logs somewhere real to go —
which the project's own stack doc already prescribes ("Spec requires file
logging with level filter", tracing-appender 0.2.5 for rolling daily files)
but which was never wired.

Output: a windowed release binary that logs to
`%APPDATA%\RemoteControl\logs\server.log.<date>`.
</objective>

- `main.rs:53` is `tracing_subscriber::fmt().with_env_filter(...).init()` —
  stdout only. `tracing-appender` is NOT in `server-windows/Cargo.toml`.
- Exactly two `println!` sites exist, both in `notify.rs`: the pairing PIN
  (line 22) and the already-running notice (line 48).
- The PIN's console print is now redundant. `shell/pair_window.rs` renders the
  PIN as digit boxes ("ENTER THIS PIN ON YOUR PHONE") plus a QR code, so the
  GUI is the guaranteed path the console print used to be. Its doc comment
  still claims otherwise and must be corrected rather than left lying.
- Threat T-03-04 stands: the PIN goes to stdout + toast + the pair window,
  NEVER through tracing. Adding a file sink must not become a way for the PIN
  to reach a log file.
- `config.rs:104` resolves `%APPDATA%\RemoteControl\config.toml` via
  `dirs::config_dir()`, degrading to a relative path rather than panicking on a
  missing known folder. The log directory follows the same pattern.
- `cfg_attr(not(debug_assertions), ...)` is the right gate: `cargo run` during
  development keeps its console and its stdout logs; only release builds go
  windowed.
</context>

  <files>server/server-windows/Cargo.toml, server/server-windows/src/config.rs, server/server-windows/src/logging.rs, server/server-windows/src/main.rs</files>
  <action>
Add `tracing-appender = "0.2"` to `server-windows/Cargo.toml` with a comment
matching the file's convention (why it exists: the console is gone in release,
so the file IS the log).

`config.rs`: add `log_dir() -> PathBuf` returning
`dirs::config_dir()/RemoteControl/logs`, mirroring `config_path()`'s
`unwrap_or_default()` degrade-never-panic behaviour. Keep it next to
`config_path` so both known-folder resolutions live together.

New `server/server-windows/src/logging.rs`:

- `pub fn init() -> Option<WorkerGuard>`.
- Build the `EnvFilter` exactly as `main.rs` does today (`RUST_LOG`, else
  `info`) so the filter behaviour does not change.
- Try to `create_dir_all(config::log_dir())`. On success build a
  `tracing_appender::rolling::daily(dir, "server.log")` wrapped in
  `non_blocking`, and add a `fmt::layer()` with `with_ansi(false)` (escape
  codes in a file are noise) over that writer.
- Add a stdout `fmt::layer()` ONLY under `cfg!(debug_assertions)`. Use
  `Option<Layer>`'s own `Layer` impl (`cfg!(...).then(...)`) rather than
  duplicating the whole builder behind `#[cfg]`.
- If the directory cannot be created, install the subscriber with no file
  layer and log a warning — a broken log path must never stop the server.
  Same degrade-never-crash discipline as `config::load` and `machine_guid`.
- Document that the returned `WorkerGuard` MUST be held for the process
  lifetime: `non_blocking` writes on a background thread, and dropping the
  guard early silently truncates the tail of the log — the exact records that
  matter when diagnosing a crash.

`main.rs`: replace the step-2 subscriber block with `let _log_guard =
logging::init();` bound at `main` scope (next to `_instance_guard`), keeping
the existing security comment about what may be logged.
  </action>
  <verify>cargo build --release -p server-windows; cargo test -p server-windows</verify>
  <done>Logs land in %APPDATA%\RemoteControl\logs; dev builds still print to stdout.</done>
