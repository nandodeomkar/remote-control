# Quick 260815-a27: Fix the tray flyout clipping its bottom rows — Summary

The tray flyout now measures its own content and resizes to it, re-anchoring so
the bottom edge stays a constant 12px above the work area — `Quit` is reachable
while a phone is connected.

**Status: INCOMPLETE — halted at the blocking owner hardware check (Task 3).**
Both code tasks are done, committed and green. Task 3 cannot be performed by an
agent: it is a tray flyout on the owner's desktop, and it has not been simulated
or assumed. This summary is `status: incomplete` until the owner confirms.

## What was wrong

`flyout.rs` pinned the window at `(344.0, 398.0)` while `render` draws the
connected-device card only `if conn > 0` — roughly 60 logical px. 398 fits the
disconnected panel and overflows the connected one, and egui clips the
remainder: `Settings` sliced in half, `Quit` gone entirely. While any phone was
connected there was no way to quit from the tray, which is every UAT session.

## Task 1 — pure geometry, tests first (`8cb9fd5`)

Genuine RED first: the seven tests were written against `todo!()` bodies and
observed failing (7 failed / 0 passed) before any implementation existed, so
each test is known to actually exercise the code it names.

- `next_height(content, current, max) -> Option<f64>` — the resize decision.
  Non-finite bail (`Rect::NOTHING` reports `max.y == -inf`), upper bound
  `max_h.max(MIN_HEIGHT)` so `clamp` cannot panic on a tiny work area, and a
  `HEIGHT_EPSILON = 1.5` tolerance.
- `anchor_bottom_right(size, right, bottom, gap)` — the arithmetic previously
  inlined in `position_above_tray`, lifted so the invariant is assertable.
- `WorkArea` + `work_area(window)` — the `SPI_GETWORKAREA` read and its monitor
  fallback, now also reporting `height`, since two call sites need it. The
  existing SAFETY comment was carried over verbatim.
- `SIZE` replaced by `WIDTH` + `INITIAL_HEIGHT`.

All seven plan-specified tests landed with the plan's names and assertions.
`the_bottom_edge_never_moves` is the whole bug in one assertion — it pins
`y + height == bottom - gap` at both 398 and 458.

## Task 2 — measure, resize, re-anchor (`33b15d5`)

- `render` returns `ui.min_rect().max.y`. That `ui` is egui's root ui, so this
  is exactly what `Context::globally_used_rect()` records — no `glwin.rs`
  change, no return-value plumbing through the shared window type, no risk to
  the other three shell windows. `max.y` not `height()`.
- `Flyout::redraw` captures it the same way `actions` is captured and calls
  `fit_to_content`, which converts to logical px, clamps against the work area
  and calls `request_inner_size`.
- `Flyout::resize` re-anchors via `position_above_tray`. This is half the fix:
  `request_inner_size` reaches `SetWindowPos` with `SWP_NOMOVE`, so an unmoved
  window grows downward and buries the newly-revealed rows under the taskbar.

egui clips *painting*, not layout — that is why the overflowing panel still
reported the height it wanted, and why the defect was measurable at all.

## Deviations from Plan

**1. [Rule 3 - Blocking] The plan's gate commands select the wrong toolchain**

- **Found during:** Task 1, first test run.
- **Issue:** The plan says to run `cargo test --manifest-path server/Cargo.toml`
  from the repo root. `rustup` resolves `rust-toolchain.toml` from the *current
  directory*, not from `--manifest-path`, and the pin lives at
  `server/rust-toolchain.toml`. From the repo root the default 1.89 toolchain is
  selected and the build dies before compiling anything:
  `ecolor/egui/emath/epaint@0.35.0 requires rustc 1.92`.
- **Fix:** Ran every gate as `cargo +1.97.0 …`, matching the pin in
  `server/rust-toolchain.toml`. No file changed; this is a command-line
  correction only. Running the gates from inside `server/` works equally well.
- **Files modified:** none.

**2. [Structural] `request_inner_size` sits in `fit_to_content`, not inline in
`redraw`**

The plan sketched the resize decision inline in `Flyout::redraw`. It is instead
a private `Flyout::fit_to_content(content_h)` called from `redraw` immediately
before `actions` is returned — identical call path and ordering, but it keeps
the `SWP_ASYNCWINDOWPOS` / idempotent-re-request reasoning attached to the code
it justifies. Worth noting because the plan's gate is worded as
"`request_inner_size` returns a hit **inside `Flyout::redraw`**": the literal
grep hit is inside `fit_to_content` (`flyout.rs:257`), which `redraw` calls
unconditionally. The gate's intent — the resize happens on the redraw path — holds.
