<objective>
Browser tab list + switching on the phone's Browser screen, fed by a new MV3
Chrome/Edge extension ("Tab Bridge") that talks to the Rust server over a
SECOND, 127.0.0.1-only WebSocket listener (default port 17779 — verified
free: WS is 17777, beacon is 17778). The server relays tab state to the phone
over the existing protocol as an additive `tabs.*` message family
(protoVersion 1.3 → 1.4). Tap a tab = switch; swipe or long-press = close.
When the extension is not connected, the tab section shows an install hint
and every existing key-macro control keeps working. The existing `browser`
C→S macro message is untouched.

Resolved open questions (from RESEARCH.md, settled during planning):
1. Ext port 17779 confirmed collision-free (`DEFAULT_BEACON_PORT = 17778` in
   server-core/src/transport/beacon.rs:30; WS `DEFAULT_PORT = 17777`).
2. Router wiring: a new `Tabs` executor-trait entry in `Executors` (uniform
   pause-drop wiring — SPEC §11 lists executor-bound families, and
   `is_executor_bound` is the single gate). A core-owned `TabsRelay`
   implements it over a watch receiver (list reads) + an mpsc ExtCmd sender
   (activate/close, fire-and-forget try_send). Mirrors how WinApps pairs a
   command sender with a snapshot receiver.
3. `tabs.list` with the extension never connected replies
   `{connected:false, tabs:[]}` immediately (the watch default) — the phone
   gets its hint state on screen open with zero extra machinery.

Also discovered during planning: protocol/SPEC.md is STALE — its header still
says protoVersion "1.1" and it lacks the 1.2 (WindowInfo icon/path) and 1.3
(input.blocked) amendments that both codecs already implement
(session.rs:54 = "1.3"). Task 2 fixes this drift as part of the 1.4 amendment
so the wire contract document is honest again.

Purpose: the last Remote Mouse parity gap on the Browser screen — see and
control actual PC browser tabs from the phone.
Output: `extension/` (new top-level artifact, vanilla JS, zero deps), SPEC
1.4 + `protocol/fixtures/tabs/` + both codecs, server-core ext listener +
relay plumbing + tests, Flutter tab list UI + tests, READMEs.
</objective>

<wire_contract>
Single source of truth for Tasks 1–4 (Task 2 canonicalizes it in SPEC.md;
Task 1 writes the extension against it BEFORE the SPEC lands — shapes below
are final unless the Task-1 smoke test invalidates an MV3 assumption).

Phone ↔ server (additive protoVersion 1.4, `{t, seq?, p}` envelope):
- `tabs.list`   C→S request: p = {} ; S→C reply: p = {connected: bool, tabs: [TabEl]}
- `tabs.changed` S→C push:   p = {connected: bool, tabs: [TabEl]} — on any tab change AND on extension connect/disconnect
- `tabs.activate` C→S:       p = {id: integer} — executor-bound (pause-dropped), fire-and-forget, no err reply
- `tabs.close`  C→S:         p = {id: integer} — executor-bound (pause-dropped), fire-and-forget, no err reply

TabEl = {id: integer, title: string, active: bool, icon?: string} — icon is
base64 PNG WITHOUT a data: prefix (exact WindowInfo.icon convention). NO url
field ever crosses the phone-facing wire (privacy: titles are enough).

Extension ↔ server (localhost leg, same envelope, spec-prose only — no
fixtures; one Rust impl + one JS impl):
- `ext.hello`  ext→srv: p = {extVersion: string} — first frame after connect
- `tabs.state` ext→srv: p = {tabs: [TabEl]} — full snapshot, never a diff
- `ext.ping`   ext→srv: p = {} ; `ext.pong` srv→ext: p = {} — 20s keepalive
- `tabs.activate` / `tabs.close` srv→ext: p = {id} — same payload as phone-facing

Extension-side caps (before send): max 50 tabs; max 4096 base64 chars per
icon (drop icon to absent above); if the serialized tabs.state frame exceeds
57344 bytes (56 KB), strip icons from the END of the list until under — the
server's 64 KB WS cap (SPEC §13) applies per-listener and a capped read kills
the ext session.
</wire_contract>

|----------|-------------|
| LAN → ext listener | A LAN peer attempting to reach the extension port |
| local process → ext listener | Any process on the PC can dial 127.0.0.1:17779 |
| extension → server | Browsing data (titles, favicons) crosses to the server |
| server → phone | Tab state crosses the existing authed WS |
| phone → PC browser | tabs.activate/close drive real browser actions |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-TABS-01 | Spoofing | ext listener | mitigate | Bind 127.0.0.1 ONLY (kernel-enforced — a LAN device cannot complete the TCP handshake) + is_loopback assert in the accept arm; never a role handshake on the LAN-exposed listener |
| T-TABS-02 | Info disclosure | session.rs tabs push | mitigate | tabs.changed select! branch authed-gated (== AuthState::Authed, T-06-01 clone); tabs.list only reachable post-auth via router gate 1 |
| T-TABS-03 | Info disclosure | logs | mitigate | No tab title/url in any server log sink (T-01-31 discipline, code-reviewed in Task 3); extension console logs counts/lifecycle only; NO url field on the phone-facing wire at all |
| T-TABS-04 | DoS | ext listener frames | mitigate | 64 KB WS caps per-listener (SPEC §13); extension-side 50-tab/4KB-icon/56KB-frame caps; server-side 50-tab truncation belt; watch channel is latest-value-only (bursts coalesce); oversize-frame regression test in ext_relay.rs |
| T-TABS-05 | Tampering | local process feeding fake tabs.state / receiving activate ids | accept | A malicious local process already owns the machine — consistent with the v1 LAN threat model (SPEC §12); documented in the new SPEC §15 |
