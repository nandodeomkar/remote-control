relaunch it from the Start Menu or a desktop icon instead of digging through
`server/target/release/`.

build directory. Quitting from the tray leaves no launcher anywhere, and the
HKCU `...\Run` autostart value points at
`C:\Users\omkar\Projects\Remote Control\server\target\release\server-windows.exe`

error.

Output: `installer/RemoteControl.iss` + `installer/build-installer.ps1`
producing `dist/RemoteControl-Setup-v<version>.exe`, plus a single-instance
guard in the binary and updated distribution docs.

<context>
Established facts (do NOT re-derive):

- `auto-launch` 0.6 writes the Run value as `format!("{} {}", app_path, args.join(" "))`
  — **unquoted**, trailing space (vendored source `src/windows.rs:77`). Its
  `is_enabled()` only checks that the value NAME exists (`get_string(app_name)`),
  never the value's content, and `disable()` removes by name. So the installer
  may safely write a QUOTED path: the in-app toggle still reads it as enabled and
  can still turn it off. The space-free install directory is the second layer of
  defence, because the app's own toggle rewrites the value unquoted at
  `current_exe()`.
- `auto-launch` also writes `...\Explorer\StartupApproved\Run`; a value there whose
  last 8 bytes are non-zero means "disabled in Task Manager". Deleting the value
  restores the enabled default (its `is_task_manager_enabled` returns true on
  E_FILENOTFOUND).
- Config/data dir is `dirs::config_dir()/RemoteControl` = `%APPDATA%\RemoteControl`
  (`config.rs:104-110`), i.e. Inno's `{userappdata}\RemoteControl`.
- `windows` 0.62 `CreateMutexW` returns `Ok(handle)` even when the mutex already
  exists — it only `Err`s on an invalid handle. The already-running signal is
  therefore `GetLastError() == ERROR_ALREADY_EXISTS` read after a successful call.
  `CreateMutexW` is gated on the `Win32_Security` feature, which is already enabled.
- Renaming the shipped exe to `RemoteControl.exe` is safe: the browser extension
  talks WebSocket (no native-messaging host manifest), and no Rust source
  references the exe filename.
- `notify.rs` already owns all toast calls (`notify_pin`, `notify_firewall_warning`)
  using `Toast::POWERSHELL_APP_ID`.
- Inno Setup 6.7.3 is installed per-user at
  `C:\Users\omkar\AppData\Local\Programs\Inno Setup 6\ISCC.exe`.

Version single source of truth: `server/server-windows/Cargo.toml` `version`.
It is currently the scaffold default `0.1.0` while the shipped release is
v1.3.0-rc1; bump it to `1.3.0` so the embedded VERSIONINFO, the installer
version, and the output filename all agree. `build-installer.ps1` parses it and
accepts a `-Version` override.
</context>

<task type="auto">
  <name>Task 1: Single-instance guard in server-windows</name>
  <files>server/server-windows/src/single_instance.rs, server/server-windows/src/main.rs, server/server-windows/src/notify.rs</files>
  <action>
New module `single_instance.rs`:

- `pub struct InstanceGuard(HANDLE)` holding the mutex handle, `Drop` closing it
  via `CloseHandle`.
- `pub const MUTEX_NAME: &str = "RemoteControl.SingleInstance"` documented as
  shared VERBATIM with the installer's `AppMutex` directive — changing one side
  without the other silently breaks the installer's "close the running copy"
  detection.
- `pub fn acquire() -> Option<InstanceGuard>`: `CreateMutexW(None, false, w!(...))`.
  On `Ok(handle)` read `GetLastError()`; `ERROR_ALREADY_EXISTS` ⇒ close the handle
  and return `None` (another instance owns it). On `Err` (handle creation genuinely
  failed) return `Some` of a null-handle guard — i.e. FAIL OPEN: a broken mutex must
  never stop the owner from starting their server. Document that reasoning inline.
- Unnamed-namespace note: the name carries no `Global\` prefix on purpose, so the
  mutex is per-logon-session — two different Windows users may each run their own
  copy, which is correct for a per-user app.
- Unit test: `acquire()` returns `Some` on first call; a second `acquire()` while
  the first guard is alive returns `None`; after dropping the first guard a fresh
  `acquire()` returns `Some` again. Guard the test name so it cannot collide with
  a real running instance — use a test-only name parameter (`acquire_named`) with
  the public `acquire()` delegating to it.

`notify.rs`: add `pub fn notify_already_running()` — a short toast
("Remote Control is already running" / "Look for the icon in the tray near the
clock.") following the existing best-effort pattern (generic `warn!` on failure,
no interpolated secrets).

`main.rs`: declare `mod single_instance;` and insert the check as step 2a —
AFTER the tracing subscriber is initialised (so the exit is logged) and BEFORE
any config load, thread spawn, or bind. On `None`: `tracing::warn!` +
`notify::notify_already_running()` + `return Ok(())`. Exiting `Ok` matters — a
duplicate launch is expected user behaviour once a desktop icon exists, not an
error. Bind the returned guard to a named local (`_instance_guard`) that lives for
the whole of `main` so the mutex is held until the process exits.
  </action>
  <verify>cargo build --release -p server-windows; cargo test -p server-windows</verify>
  <done>Second launch of the release exe exits silently with the first still serving; suite green.</done>
</task>
