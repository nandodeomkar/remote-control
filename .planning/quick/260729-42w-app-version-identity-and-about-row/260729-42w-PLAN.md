<objective>
Give the app a real version identity before v1.3.0 is promoted to stable.

Problem: `pubspec.yaml` has said `version: 1.0.0+1` since the v1.0 release,
and `android/app/build.gradle.kts` feeds `versionCode`/`versionName` straight
from it. Every APK shipped since — v1.1.0, v1.2.0, v1.3.0-rc1 — therefore
declares itself version 1.0.0, versionCode 1. Android's Settings > Apps shows
"1.0.0" no matter which build is installed, versionCode has never incremented
(no upgrade ordering, and a future store listing needs monotonic codes), and
the app's own UI shows no version at all. When a friend reports a problem
there is no way to establish which build they are running.

Output: pubspec version bumped, plus an About group in Settings that reads the
version from the installed package.
</objective>

<context>
Established facts (do NOT re-derive):

- `app/remote_control/android/app/build.gradle.kts:36-37` sets
  `versionCode = flutter.versionCode` / `versionName = flutter.versionName`,
  i.e. the Flutter Gradle plugin's read of pubspec's `version: <name>+<code>`.
  Bumping pubspec is the whole fix for the Android side.
- Four builds have shipped (v1.0.0, v1.1.0, v1.2.0, v1.3.0-rc1), all at
  versionCode 1. `1.3.0+4` is coherent and monotonic; existing installs at
  code 1 upgrade cleanly.
- `settings_screen.dart` house rules: every string is a `const k...` at the top
  of the file (no inline literals), typography uses the private `_rowTitle` /
  `_rowSubtitle` roles, and groups are `_GroupSurface` widgets composed in the
  `ListView` at line ~128. `_AccentGroup` (label left, value right, static) is
  the closest structural analog for a display-only row.
- `settings_screen_test.dart` asserts the groups render in order by comparing
  `getTopLeft().dy` across a fixed label list. Appending a sixth group below
  Accent does not break it, but the test name and list say "five" and must be
  updated to stay honest.
- The suite runs under `flutter_test` with no platform channels: the existing
  test installs `InMemorySharedPreferencesAsync`. `PackageInfo.fromPlatform()`
  would throw `MissingPluginException` there, which is why the version is
  exposed as a Riverpod `FutureProvider` — tests override the provider and
  never touch the plugin.

Dependency note: `package_info_plus` is the fluttercommunity "plus" plugin,
same family as the already-vendored `wakelock_plus`. It reads Android's
PackageManager, needs no new permission, and adds no runtime surface beyond a
single platform call.
</context>

<risks>
- versionCode 4 is a one-way door: Android refuses to install a lower code over
  a higher one. Anyone who somehow needs to go back to an older APK must
  uninstall first. Acceptable — that is the point of monotonic codes.
- Adding a plugin changes the Android build graph. `flutter build apk` is not
  run here (release signing is an owner step); `flutter analyze` plus the suite
  are the gates, and the plugin is a first-party fluttercommunity package with
  no manifest requirements.
</risks>
