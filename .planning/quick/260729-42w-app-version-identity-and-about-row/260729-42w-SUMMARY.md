# Quick Task 260729-42w — App version identity + Settings About row

## Problem

`pubspec.yaml` said `version: 1.0.0+1` from the v1.0 release onward, and
`android/app/build.gradle.kts:36-37` feeds `versionCode`/`versionName` straight
from it. The v1.1.0, v1.2.0, and v1.3.0-rc1 APKs all declared themselves
version 1.0.0, versionCode 1.

Consequences: Android's Settings > Apps showed "1.0.0" regardless of the
installed build, versionCode never incremented (no upgrade ordering, nothing a
store would accept), and the app showed no version anywhere in its own UI. A
friend reporting a problem could not be asked which build they were on.

Surfaced while reviewing the app ahead of promoting v1.3.0-rc1 to stable.

## What shipped

**Task 1 — version identity** (`dd36943`)

`version: 1.3.0+4` with a comment recording that the build number is Android's
versionCode and must only ever increase. `package_info_plus ^10.2.1` added
(fluttercommunity "plus" family, same vendor as the already-vendored
wakelock_plus; no new permission).

**Tasks 2 & 3 — About row + tests** (`cf7005c`)

`lib/settings/app_version.dart` exposes `appVersionProvider`, a
`FutureProvider<String>` returning `'<version> (<buildNumber>)'`. Settings gains
`_AboutGroup` as group 6, mirroring `_AccentGroup`'s label/value shape.

Four new tests: the format helper, the happy path, the degraded path, and the
in-flight path.

## Surprises / notes

- **Riverpod 3 auto-retries failed providers** with exponential backoff. The
  degraded-path test failed at first because the state oscillated out of
  `AsyncError` back into `AsyncLoading` before the assertion ran.
  `retry: (_, _) => null` fixes the test and is the correct production
  behaviour — the package manifest cannot change while the process is alive, so
  a failure is permanent and retrying would spin a timer forever.
- A sixth group overflows the default 800x600 test viewport, and `ListView`
  builds lazily — `find.text('About')` found nothing because the widget did not
  exist. The order assertion compares `dy` across all six simultaneously, so
  scrolling was not an option; the test sizes the viewport up instead.
- `Override` is not an exported type name in this Riverpod version. The test
  host takes a `Future<String> Function()` and builds the override internally.

## Follow-up not done

The third suggestion from the pre-promotion review is untouched: **silent
keymap skew**. App and server both claim protocol 1.5, but v1.3.0 grew the
keymap by 18 codes with no protocol bump, so a phone updated without its server
gets a Shortcuts tile that silently no-ops. `AuthOkMsg` carries no server
version, but `protocol/BEACON.md` already specifies that unknown beacon fields
are ignored and additive fields do not bump `v` — so adding a server version to
the beacon is a backward-compatible change. Its own quick task.
