# Quick Task 260729-58x — Tab-group visual hierarchy

Grouped tabs now render inside one group-tinted, group-bordered `_GroupBlock`
per consecutive run, with nested radius-10 rows and a 16px run gap, so a group
has a visible END and the tab after it is unmistakably outside.

## What Changed

**Problem.** The 260716-sme design put a floating `_GroupHeader` label above
otherwise-flat rows. That gave a group a visible START but nothing marking
where it stopped — every row, in or out of the group, was identical radius-16
`kSurface` chrome at an identical 8px pitch. The user's report ("hard to tell
if a tab is in a group or just after it") was a direct consequence.

**Fix.** `_TabsSection.build` now chunks `tabs.tabs` into consecutive
same-group runs (`_TabRun { GroupInfo? group; List<TabInfo> tabs; }`) instead
of tracking `prevGroupId` inline:

- A **grouped run** emits one `_GroupBlock`: `Container` with 6px padding,
  `groupColor(...).withValues(alpha: 0.06)` fill, `Border.all(... alpha: 0.40)`
  and radius 16, holding the `_GroupHeader` plus the run's rows at 6px pitch.
- An **ungrouped run** emits its rows directly at radius 16 with 8px gaps —
  byte-identical rendering to before.
- Runs are separated by 16px (never before the first).

`_TabRow` gained a required `radius` field driving both the `Material` shape
and the `InkWell` splash clip; the shared `_TabsSection._row(tab, radius:)`
builder passes the same value into the `Dismissible` background so the panel
revealed under a swiping row matches the row's corners. Every behavior around
it — `ValueKey(tab.id)`, `DismissDirection.horizontal`, the `_confirmSwipe`
spring-back, the `enabled` gating, tap-down activate, the 100ms accent
press-flash, long-press close, `minHeight: 56` — is untouched.

`_GroupHeader` gained a required `count` rendered as a separate
`Text('· $count')` at 12/400 `kMuted`, and its outer padding moved from
`EdgeInsets.only(left: 4)` to `only(left: 6, top: 2, bottom: 6)` so the header
sits correctly inside the block's padding. The collapsed branch is unchanged:
still exactly one `Opacity(0.5)` around the content row plus the
`Symbols.unfold_less_rounded` glyph.

Library, `_TabsSection`, `_GroupBlock`, `_GroupHeader` and `_TabRow` doc
comments were rewritten/extended to house density: run chunking, the 16/8/6
spacing contract, the flat fallback for unresolved group ids, the tint/border
derivation, the concentric-radius rule, and why a container was the missing
signal.

## Tests

Four new `testWidgets` in a new `group('tab-group visual hierarchy
(260729-58x)')`, plus module-level `_blockDecoration` / `_rowRadius` helpers
and a `_twoGroups` run-boundary fixture — all reusing the existing
`_FakeService` / `_pumpScreen` / `_unmount` / `_rowBorder` / `_groupedTabs`
seams:

1. Block fill = `blue.withValues(alpha: 0.06)`, border = 40% at width 1,
   outer radius 16; `GitHub`/`PRs` rows at radius 10 while `Docs` (the tab
   after the group) stays 16; `GitHub` keeps its `kAccent` active border.
2. Two adjacent groups produce two blocks with differing tints (proof the
   chunker split at the run boundary) and one header each — plus an assertion
   that an EXPANDED group introduces **no** `Opacity` ancestor, which is what
   keeps the pre-existing collapsed-header single-Opacity lookup unambiguous.
3. `· 2` exists as its own `kMuted` Text while `find.text('Work')` still
   matches exactly one widget tinted `kGroupColors['blue']`.
4. An untitled group falls back to dot + `· 1`, reaching the block decoration
   through the count Text.

RED run: exactly 4 failures, all 18 pre-existing tests in the file green
