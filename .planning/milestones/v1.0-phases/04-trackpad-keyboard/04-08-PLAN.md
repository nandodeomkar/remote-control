<objective>
Close verification gap 2 (04-VERIFICATION.md, blocks roadmap SC5 / KEY-04; open
security threat T-04-04): `KeyboardPanel` tracks at most ONE held key cap —
`_heldCode` is a single `String?` (keyboard_panel.dart:105). Each `_KeyCap` has
its own GestureDetector and Flutter tracks pointers independently, so two caps
can be concurrently pressed. Ordinary key rollover (press Down before releasing
Right — the normal arrow-key pattern) overwrites the slot; the first key's
release hits the `_heldCode != code` guard (line 188) and its `up` is swallowed.
That key stays held server-side, and Windows autorepeats it into the focused app
indefinitely (review CR-02, independently confirmed by the verifier) — sustained
unintended keystroke injection from a routine gesture.

Fix (verification gap 2 "missing" item 1): track held caps as a `Set<String>`.
`_onKeyDown` adds + sends down; `_onKeyUp` sends up only if `remove(code)`
returns true; `_onDisconnected` clears the set — preserving the D-12
skip-stale-ups semantics (CONN-07 release_all already freed the real keys; a
queued stale up must never flush into a NEW session) for ANY number of held
caps, and preserving D-11 (autorepeat is server-side down/hold/up — the fix
changes only client bookkeeping, never the wire vocabulary).

Additionally folds IN-04, as 04-SECURITY.md's T-04-04 row explicitly directs
("Fold IN-04 into same fix"): `_KeyCap` currently nulls `onTapUp`/`onTapCancel`
when `enabled` is false (key_rows.dart:412-413), so an `enabled` flip mid-press
disposes the release handlers and swallows the up client-side — the same
stuck-key class through a different door. Release handlers become always-wired;
a `_live` press-lifecycle flag keeps presses that started disabled inert (the
existing gated-inert tests must stay green).

Purpose: KEY-04 "stops immediately on release" holds under multi-finger
reality, not just single-cap tests; closes security threat T-04-04 so
04-SECURITY.md can be signed off (together with 04-07's T-04-03 closure).
Output: set-based held tracking + always-wired release path + three regression
tests; full Flutter suite green.
</objective>

## Phase Goal

**As a** laptop owner, **I want to** use my phone as a precise mouse and full keyboard for my Windows laptop, **so that** it replaces a real trackpad and keyboard — not a toy.

This plan repairs the held-key slice of that story: holding and rolling between
keys must behave like a real keyboard — every release stops its own key,
nothing is ever left autorepeating on the PC.
