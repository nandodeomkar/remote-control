<task type="checkpoint:human-verify" gate="blocking">
  <what-built>
    The full end-to-end cursor vertical is now runnable: the server-windows binary
    (02-01) injects the real cursor behind auth; the Flutter client (02-02 + 02-03)
    connects over a TCP_NODELAY WebSocket, completes the real Phase-1 handshake,
    sends raw 1:1 move frames from finger drags once Authed, and displays live
    p50/p95 round-trip-under-load. Nothing further is automatable — the remaining
    question is purely physical: does it feel instant and does p95 stay under 30ms
    on real WiFi?
  </what-built>
  <how-to-verify>
    Do this on the owner's phone + Windows laptop on the SAME WiFi, phone OFF the
    charger (battery power can add power-save latency — RESEARCH pitfall):

    1. On the laptop: `cargo run -p server-windows`. Note the printed `Pairing PIN`
       and the laptop's LAN IP (`ipconfig`). The server listens on :17777.
    2. On the phone: `flutter run` (or install the debug APK). Enter the laptop IP
       and port 17777, tap Connect, and type the PIN shown on the console.
    3. Confirm the HUD shows "Authed" and a live p50/p95.
    4. CRITERION 1 (visually instant): drag your finger on the trackpad. The PC
       cursor should track with NO perceptible lag. PASS/FAIL by feel.
    5. CRITERION 2 (<30ms E2E under load): while dragging continuously for ~15-20s,
       read the HUD p50 and p95. Record both numbers. GATE = p95 < 30ms.
    6. CRITERION 3 (no 40-200ms hitches): do a SLOW, precise 1px-at-a-time drag and
       a slow diagonal. Watch for stutters/freezes. PASS = smooth, no visible
       40-200ms hitches; the HUD p95 tail should not spike.
    7. CRITERION 4 (smooth diagonal, sub-pixel + DPI): drag slowly along a diagonal;
       the cursor should track smoothly with no drift or stair-stepping. Re-check on
       a 150%-scaled display if available (DPI awareness cross-check).
    8. Record the four judgments + measured p50/p95 in
       `.planning/phases/02-end-to-end-cursor-spike/02-04-GATE-RESULT.md`.

    If p95 >= 30ms OR criterion 1/3/4 fails: the gate FAILS. Do NOT advance to
    Phase 3 — the roadmap requires opening the UDP-mouse-channel reconsideration
    (behind the existing transport abstraction) first. Note whether hitches look
    power-save-shaped (periodic, off-charger only) vs Nagle-shaped
    (traffic-pattern-dependent) to inform that decision.
  </how-to-verify>
  <resume-signal>
    Type "pass" with the recorded p50/p95, or "fail" describing which criterion
    missed and the observed numbers.
  </resume-signal>
</task>
