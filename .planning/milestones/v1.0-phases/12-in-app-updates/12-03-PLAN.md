<objective>
Bring the public mirror repo into existence and put one real release into it, produced
by `tools/release.ps1` rather than by hand — then rewrite `DISTRIBUTION.md` around the
new procedure.

D-21 makes this the gate for every client-side leg of the phase: nothing on the phone,
the server or the extension is testable end to end until a real published release
exists to check against. The repo is an outward-facing, account-level action the owner
must perform, so this plan is **not autonomous** and opens with an explicit human
action naming exactly what to create.

Purpose: an anonymous client with no token can read "what is the latest version"
(D-01, D-02) — which is the only reason the mirror exists.
Output: a live public repo, one published release, the three version files bumped and
committed, and an updated `DISTRIBUTION.md`.

**Why wave 3, and why it depends on 12-06.** Running `tools/release.ps1` REWRITES
`server/server-windows/Cargo.toml`, `app/remote_control/pubspec.yaml` and
`extension/manifest.json` (D-20) — this plan owns those three files, not just
`DISTRIBUTION.md`. `12-06` adds the `ureq` dependency to that same `Cargo.toml`, so the
two cannot run in one wave. Placing this plan after 12-06 also makes the published
artifact deterministic: it is built from the end-of-wave-2 tree, at a commit this plan
records by sha, rather than from a tree a sibling plan may be halfway through editing.

**What v1.5.0 does and does not contain.** It is built from the end of wave 2, so it
carries the 1.8 codecs, the `UpdateExecutor` trait, the feed/download modules and the
Android install channel, but NOT the router arms, the update thread or the Updates
screen. That is expected and is not a defect: v1.5.0 exists to satisfy D-21 — to be a
real, anonymously readable release for the later client-side plans to check AGAINST.
The first release that can actually be tapped is `1.6.0`, published by `12-18` from the
finished tree.

**Known one-time cost, not a defect:** both already-installed clients predate this
update path, so the first upgrade onto it is still a manual install for both users. No
migration work is planned for it; it is stated as a limitation in `DISTRIBUTION.md`.
</objective>

|----------|-------------|
| owner's GitHub account -> public internet | Everything pushed to the mirror is anonymously readable forever |
| build machine -> published artifact | Anything committed or embedded can end up in a shipped binary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | the assets this release publishes | mitigate | Recorded because these are the exact files the server will later fetch and execute: the server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). This plan's contribution is that the asset names and digests are predictable and verifiable |
| T-12-02 | Information Disclosure | the public mirror repo | mitigate | Public by design and by necessity; it holds only binaries and release notes. The human-action task states explicitly that no token goes into the repo, a workflow, or an artifact. Source and `.planning/` stay in the private repo |

A release whose assets have null digests is rejected outright, because a null digest is a hard `checksum` refusal on both client paths (D-15) |
