<objective>
Add the Dart `update.*` codecs to `remote_protocol` and pin them to the same
`protocol/fixtures/update/` files the Rust codec uses, then prove the SC8
forward/backward-compatibility path explicitly.

Purpose: SPEC Sec 14 forbids per-language fixture copies. Both decoders are pinned to
one set of bytes, which is what stops a phone offering an update the server then
refuses because the two sides read the wire differently.
Output: four message classes, one nested value type, one registered fixture family,
one forward-compat test file.

**SC8 wording note, carried from RESEARCH:** "a 1.8 phone" in this phase means *the
phone knows the `update.*` types*. It does NOT mean the phone advertises `"1.8"` in
`hello`. `app/packages/remote_protocol/lib/src/version.dart` still declares
`protoVersion = '1.1'` and is deliberately left alone — changing what the client
advertises is a handshake-path behaviour change with its own test surface and is not
in this phase.
</objective>

  <action>
Add four `final class` message types to `json_codec.dart`, each extending
`RemoteMessage`, each with a `const` constructor, a `fromPayload` factory, a `t`
getter and a `toPayload` method - the `BmOpenMsg` shape.

`UpdateCheckMsg` - no fields. `t` is `update.check`. `toPayload` returns an empty map,
so the canonical form still emits `p` as `{}`.

`UpdateStatusMsg` - `serverVersion` (required String), `extConnected` (required bool),
`extVersion` (nullable String), `lastUpdate` (nullable `LastUpdate`). `t` is
`update.status`. Missing `serverVersion` or `extConnected` throws `FormatException`
with the message `missing required field: serverVersion` / `... extConnected`, matching
fixture `09`. `toPayload` OMITS null optionals entirely rather than emitting nulls.

`LastUpdate` - a small value class with `target` (String), `ok` (bool) and `error`
(nullable String), plus `fromPayload` / `toPayload` and a value-equal `operator ==`
and `hashCode` so provider state comparisons behave.

`UpdateApplyMsg` - exactly one field, `target` (required String). `t` is
`update.apply`. Add a doc comment citing D-14: this message carries a version string
and nothing else; the server resolves the asset URL and its sha256 itself, and the
phone has no way to name a file. Adding a url, asset, filename or hash field here
would be remote code execution on the PC.

`UpdateProgressMsg` - `stage` (required String), `pct` (nullable int), `version`
(nullable String), `error` (nullable String). `t` is `update.progress`. `stage` and
`error` stay plain Strings - the closed D-10 and D-11 vocabularies are rendered by the
UI copy map (12-15), not enforced by the codec, matching how the Rust side treats them.

Register all four in the `decodeText` `switch (tRaw)`, one line each, in the
`'bm.open' => BmOpenMsg.fromPayload(p),` style. Leave the
`_ => UnknownMsg(t: tRaw)` fallthrough untouched - it is the SC8 guarantee.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PC server -> phone (WebSocket) | `update.status` and `update.progress` decode here from a machine the phone does not control |
| phone -> PC server | `update.apply` is composed here; its narrowness is the phone-side half of D-14 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | `UpdateApplyMsg` | mitigate | The server resolves every asset URL and hash itself from a compiled-in repo constant and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). The phone-side type makes the omission visible: `UpdateApplyMsg` has exactly one field and no way to express a locator, so a compromised or buggy client cannot even construct the dangerous message |
| T-12-06 | Information Disclosure | `UpdateProgressMsg.error` | mitigate | Decoded as an opaque String and mapped to fixed copy by the UI (12-15). No error string is ever rendered raw, so a server that violated D-11 still could not paint a path or URL onto the screen |
| T-12-08 | Spoofing | forward compatibility | accept | `UnknownMsg` fallthrough keeps the session alive on any unrecognised `t`, by design (SPEC Sec 10). Proven by test rather than assumed |
| T-12-12 | Denial of Service | malformed `update.status` | mitigate | Missing required fields throw `FormatException` at the codec boundary rather than producing a half-built object the UI would render as truth |
| T-12-SC | Tampering | pub.dev installs | accept | This plan adds no Dart dependency. `crypto` is introduced by 12-10 and is audited in 12-RESEARCH.md Package Legitimacy Audit (publisher `dart.dev`, 160/160 pub points) |
</threat_model>
