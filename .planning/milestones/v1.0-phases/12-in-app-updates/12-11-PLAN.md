<objective>
Assemble the pieces into the update pipeline: a dedicated OS thread that owns all the
blocking work, the refusal ladder that decides what is allowed before any of it starts,
and the `UpdateExecutor` implementation that is the only thing the wire can reach.

The thread is the house pattern — `apps_thread`, `clip_thread` and `audio_thread` are
all this shape: commanded over a `std::sync::mpsc`, publishing state over a
`tokio::sync::watch`. It matters more than usual here because `ureq` is blocking;
calling it from a tokio task would stall a runtime worker for the entire download.

This plan does NOT wire anything into `Executors`, `ServerDeps` or `main.rs` — that
ripple is 12-12's. `WinUpdate` simply comes into existence, fully constructed from
injected handles.

Purpose: D-14 and D-15 stop being prose and become an ordered sequence with a test that
proves the order.
Output: `update_thread.rs`, `WinUpdate`, and unit tests for the refusal ladder.
</objective>

Write the refusal ladder as PURE functions with no I/O, so the order is testable:

`pub fn is_valid_target(target: &str) -> bool` — exactly `^\d+\.\d+\.\d+$`, anchored,
no leading `v`, no pre-release suffix, no whitespace. Document that this runs BEFORE
`target` is interpolated into a path or a generated command line, and that without it a
target of `..\..\Startup\x` reaches a filename and a target carrying a quote and an
ampersand reaches `cmd`.

`pub fn pre_fetch_refusal(busy: bool, target: &str, running: &str) -> Option<UpdateError>`
— the cheap checks, in this exact order and no other:
1. `busy` is true, return `Busy` — cheapest, no I/O (D-15).
2. `target` fails `is_valid_target`, return `Stale`. A malformed target is treated as
   "not the version I resolved", which is exactly what a forged
   `update.apply {target: "https://evil/x.exe"}` must produce (SC6).
3. `target` is not strictly greater than `running`, return `Downgrade` — a pure integer
   tuple comparison, no I/O (D-15, D-26).
Otherwise `None`.

`pub fn post_fetch_refusal(target: &str, resolved_latest: &str) -> Option<UpdateError>`
— returns `Stale` when the two differ. Document why the server trusts only what it just
fetched: the phone's cached feed can be 24 hours old, so the phone's opinion of "latest"
is advisory and the server's own fetch is authoritative.

Reuse the same integer-tuple version comparison the codebase already needs; if 12-04
placed a comparison helper in `server-core`, call it rather than writing a second one,
and record which was used. Never compare version strings lexically and never parse them
as floats: `"1.10.0" < "1.9.0"` lexically, and `1.10` is a smaller float than `1.9`.

Tests in a `#[cfg(test)]` module: `refusal_order` asserts that with `busy` true AND a
malformed target AND a downgrade all present simultaneously, the result is `Busy` — the
order is observable, not incidental; then peel each condition off and assert the next
one in the ladder surfaces. Add cases proving a target of `https://evil/x.exe`,
`..\..\Startup\x`, `1.5.0" & calc &`, `v1.5.0`, `1.5` and `1.5.0-rc1` all refuse; and
that `post_fetch_refusal` returns `Stale` for a mismatch and `None` for a match.

  <action>
Add `pub fn run_update_thread(cmd_rx: std::sync::mpsc::Receiver<UpdateCmd>, progress_tx: std::sync::Arc<tokio::sync::watch::Sender<UpdateProgress>>, busy: std::sync::Arc<std::sync::atomic::AtomicBool>)`.

The loop blocks on `cmd_rx.recv()` and handles one command at a time.

`UpdateCmd::Check` — publish `checking`, fetch the feed, then publish either
`uptodate` (when the resolved latest is not newer than `env!("CARGO_PKG_VERSION")`) or a
terminal carrying the resolved version. On a fetch failure publish `failed` with
`network`. This arm exists for the PC settings fallback (12-17); the phone's
`update.check` is answered synchronously from `UpdateInfo` and does not enter here.

`UpdateCmd::Apply(target)` — the ordered pipeline. `busy` was already set by the caller
(Task 3); this arm CLEARS it on every exit path, including every early return.
1. Publish `checking`.
2. `feed::fetch_latest` with the feed agent. A failure publishes `failed` with
   `network` and returns.
3. `post_fetch_refusal(&target, &resolved.version)` — a mismatch publishes `failed`
   with `stale` and returns.
4. `feed::resolve_asset` for the setup prefix. Absent, ambiguous or digest-less
   publishes `failed` with `installer` or `checksum` as the resolver returned.
5. Publish `downloading` with `pct` 0, then `download::download_to` into
   `download::temp_path_for(&target)`, reporting progress. Throttle to at most one
   `watch` send per 1% or per 250 ms; the watch coalesces, so a dropped tick
   re-delivers. A transport failure publishes `failed` with `network`; a write or space
   failure publishes `failed` with `disk`, and the partial file is deleted (D-23).
6. Publish `verifying`, then `download::verify_or_delete` against the asset's digest. A
   mismatch publishes `failed` with `checksum`; the file is already deleted and nothing
   is spawned (D-15).
7. Publish `installing`. `apply::begin_apply(&target, &setup_path)` writes the
   pessimistic marker and spawns the detached helper.
8. Publish `restarting` LAST, then give the session loop a brief moment to flush it
   before the process exits, so the phone can render the stage before the socket drops
   (D-17: the existing reconnect FSM takes it from there; do NOT build a second
   reconnect path). Then request process exit through whatever the crate's existing
   shutdown path is, or return a signal the caller acts on — choose one, implement it,
   and record the choice.

Every published `UpdateProgress` carries `version` for the target being applied where
it is known, `pct` ONLY on `downloading` (D-10), and `error` ONLY on `failed`, always
from `UpdateError::code` (D-11). No path, URL, HTTP status or exception text ever
enters a published value; those go to `tracing` and `update.log`.

Add a `#[cfg(test)]` test for the progress throttle as a pure helper — given a byte
count, a total and the last-emitted percent, decide whether to emit — so the 1%/250 ms
rule is testable with no download.

  from `marker::take_marker()`.

`WinUpdate::new` also calls `marker::truncate_update_log_if_large()`, so the marker read
and the log housekeeping both happen exactly once per process run.

`fn info(&self) -> UpdateInfo`:
- `server_version` from `env!("CARGO_PKG_VERSION")` (D-05) — never a hardcoded
  constant. Add the anti-constant rationale in a comment: a hand-maintained version
  string is exactly the bug that pinned the app at `1.0.0+1` across four releases.
- `ext_connected` and `ext_version` from a `borrow()` of the `ext` watch.
- `last_update` from `self.pending_marker.lock().take()` — so a marker is reported on
  exactly ONE `update.status` and never again (D-12). Document that this is why `info`
  takes rather than clones.

`fn apply(&self, target: &str)`:
- Run `pre_fetch_refusal(self.busy.load(...), target, env!("CARGO_PKG_VERSION"))`.
  On `Some(err)`, publish `UpdateProgress { stage: "failed", error: err.code(), .. }`
  on the progress sender and return WITHOUT touching the thread. This is what makes a
  second tap during a download answer `busy` immediately instead of queueing behind a
  download.
- Otherwise set `busy` to true with a compare-and-swap (not a plain store, so two
  concurrent sessions cannot both win) and `try_send(UpdateCmd::Apply(target.to_string()))`
  into the thread. A full or closed channel clears `busy` again and publishes `failed`
  with `installer`. Use `try_send`-style fire-and-forget, matching the house
  non-blocking send-and-forget rule on hot seams.
- Add a doc comment restating D-14: `target` is the only value from the wire that
  reaches this crate, it is validated inside the refusal ladder before any use, and the
  asset URL and its sha256 are resolved from a compiled-in constant in `feed.rs`.

Add tests: `info` returns `CARGO_PKG_VERSION` as `server_version`; `info` returns the
seeded marker once and `None` on the second call; `apply` with the busy flag already set
publishes a `failed`/`busy` progress value and sends nothing to the thread; `apply` with
a malformed target publishes `failed`/`stale` and sends nothing.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| phone -> `UpdateExecutor::apply` | The narrowest point in the system; one string crosses it |
| update thread -> `%TEMP%` -> installer | Bytes from the internet become a running process |
| GitHub feed -> "what is latest" | The server's own fetch, not the phone's cache, is authoritative |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | `WinUpdate::apply` and the apply pipeline | mitigate | The server resolves every asset URL and hash itself from a compiled-in repo constant in `feed.rs` and NEVER accepts, derives, or is influenced by a target supplied over the wire (D-14). The pipeline receives only a version string, and `is_valid_target` refuses anything that is not exactly three integers before that string touches a path, a URL or a command line. A forged `update.apply {target: "https://evil/x.exe"}` is refused as `stale` with zero network activity, asserted by a named test |
| T-12-35 | Tampering | downgrade attack | mitigate | `pre_fetch_refusal` refuses a target at or below `CARGO_PKG_VERSION` with an integer tuple comparison before any I/O (D-15, D-26). The phone refuses the same case independently, so there is no single bypass point |
| T-12-36 | Spoofing | replayed or stale feed | mitigate | `post_fetch_refusal` compares the phone's target against what the server itself just fetched; a mismatch is `stale`. No resolved URL is ever cached across a run |
| T-12-37 | Denial of Service | concurrent applies | mitigate | The `busy` flag is set with a compare-and-swap, refused immediately by the executor rather than queued behind a download, and cleared on every exit path including every early return - asserted by a test that drives a failing pipeline |
| T-12-38 | Tampering | unverified bytes executed | mitigate | `verify_or_delete` runs after `sync_all` and before `begin_apply`; a mismatch deletes the file and publishes `checksum`. `begin_apply` is unreachable from any earlier failure branch |
| T-12-06 | Information Disclosure | published progress | mitigate | Every `failed` publication takes its `error` from `UpdateError::code`, and a grep criterion asserts no inline error literal exists in the thread. Paths, HTTP statuses and exception text go to `tracing` and `update.log` only |
| T-12-39 | Denial of Service | blocking work on the tokio runtime | mitigate | All blocking I/O is on a dedicated OS thread, the same shape as `apps_thread`, `clip_thread` and `audio_thread`. `ureq` is never called from a tokio task |
| T-12-SC | Tampering | cargo installs | accept | No new dependency; `ureq` arrived in 12-06 with an OK legitimacy verdict |
</threat_model>
