  <action>
In `buildAndSend`'s per-tab element loop, immediately after the `groupId` assignment and before the
favicon await, add the bookmarked flag with strict tri-state semantics:

- When `bmUrlSet` is a `Set` (the tree was read successfully on this pass) AND the tab has a `url`,
  set `el.bookmarked = bmUrlSet.has(tab.url)` — an explicit `true` or `false`, never skipped.
- When `bmUrlSet` is `null` (the tree could not be read, or `chrome.bookmarks` is absent), do NOT
  set the key on ANY tab.
- When `bmUrlSet` is a `Set` but the tab has no `url` (rare, e.g. a discarded tab), do NOT set the
  key on that tab — unknown is the honest answer.

Comment the divergence explicitly: unlike `icon` and `groupId`, where absence means "there is
none", absence of `bookmarked` means UNKNOWN. Emitting `false` when the tree could not be read
would render an empty star on a page that IS bookmarked, which is exactly the misreport D-11
forbids. The cost of the explicit `false` is about 20 bytes per tab, under 2 percent of the 56 KB
budget at 50 tabs — affordable.

Use RAW EXACT string equality against `tab.url`. Do NOT normalize: do not strip fragments, do not
strip query strings, do not unify schemes, do not add or remove trailing slashes. Comment the
reason — it is blast radius, not fidelity: D-11 says unstar deletes EVERY matching-URL entry, so
any widening of "matching" would let an unstar on a base URL destroy a deliberately-kept
fragment-specific bookmark. Chrome canonicalizes both bookmark URLs and `tab.url` through the same
GURL path, so exact equality is correct for the common case; the residual mismatch (fragment,
tracking query, scheme change) reads as an empty star on a page whose base URL is bookmarked, which
is honest rather than a lie.

Do not add a per-tab `chrome.bookmarks.search({url})` call. The URL set is a free by-product of the
`getTree()` walk `buildBmSnapshot` already performs; 50 extra async IPC round-trips inside a 200 ms
debounce would double worst-case snapshot latency for identical semantics (`search({url})` is
documented as matching verbatim).

Extend the existing counts-only snapshot log so it also reports how many tabs carried a
`bookmarked` flag — a count, never a title or a URL.
  </action>

  <action>
Add one resolver plus four `case` arms in the existing `onmessage` switch. Every arm is
fire-and-forget with a terminal `.catch(() => {})` — the family has no `err` reply and every
failure self-heals on the next full snapshot.

1. `async function bookmarksBarId()` — `await chrome.bookmarks.getTree()`, take
   `tree[0] && tree[0].children` (default to an empty array), and return the id of the first root
   whose `folderType === "bookmarks-bar"`, falling back to `roots[0]` and finally to `null`.
   Comment both prohibitions with their reasons: the hardcoded id `"1"` is explicitly forbidden by
   D-10 and is not guaranteed stable across profiles; matching the title `"Bookmarks bar"` is
   locale-dependent and returns undefined on a German or Japanese Chrome, which would silently file
   the bookmark into "Other bookmarks". `folderType` is the stable documented enum
   (`bookmarks-bar | other | mobile | managed`).

2. `case "bm.open":` — `chrome.bookmarks.get(p.nodeId)` then, only if the returned node has a
   truthy `url`, `chrome.tabs.create({ url: node.url })`. Guard `if (!node.url) return;` explicitly:
   a folder node has no URL and `tabs.create({url: undefined})` opens the new-tab page, a confusing
   no-op. The phone should never send a folder id (folder rows drill down, they do not open) but the
   extension is the tier that must not trust its input — `p.nodeId` is an opaque untrusted string
   from the LAN peer. Terminal `.catch(() => {})`.

3. `case "bm.star":` — `chrome.tabs.get(p.tabId)`, require a truthy `tab.url`, resolve
   `await bookmarksBarId()`, and `chrome.bookmarks.create({ parentId, title: tab.title || tab.url,
   url: tab.url })`. If the parent id resolves to `null`, do nothing rather than creating an
   unparented bookmark. Terminal `.catch(() => {})`.

4. `case "bm.unstar":` — `chrome.tabs.get(p.tabId)`, require a truthy `tab.url`,
   `chrome.bookmarks.search({ url: tab.url })`, and for EVERY returned node that is not
   `unmodifiable`, call `chrome.bookmarks.remove(node.id).catch(() => {})` individually. The
   per-node catch is required: a managed node rejects with a modify-managed error and a
   concurrently-deleted node rejects with a no-node error, and neither may abort the remaining
   removals. Comment that `search({url})` matches verbatim and that folders have no URL, so a
   folder can never appear in these results — D-11's "delete every matching entry" therefore cannot
   interact with D-14 at all.

5. `case "bm.remove":` — `chrome.bookmarks.remove(p.nodeId).catch(() => {})`. Nothing else. Comment
   that `removeTree` is deliberately never used (D-14), that Chrome itself rejects a non-empty
   folder with its folder-not-empty error, that the roots reject with the modify-special error, and
   that managed nodes reject with the modify-managed error — three independent backstops behind the
   phone-side affordance gate. A subtree wipe is therefore structurally impossible from this
   extension.

Every arm must trigger a refreshed snapshot naturally through the existing
`chrome.bookmarks.on*` listeners — do not call `scheduleSnapshot()` directly from a command arm.
No arm may log a URL, a title, or a node id.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server → extension (`nodeId`, `tabId`) | Values that originated on the phone, an authed but remote LAN peer; untrusted at this tier |
| extension → Chrome bookmark database | The only place in the system where bookmarks are destroyed |
| bookmark URL set → tab snapshot | The only place a URL influences what leaves the machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-10 | Tampering | `bm.open` on an untrusted `nodeId` | mitigate | `chrome.bookmarks.get(p.nodeId)` then an explicit `if (!node.url) return;` before `tabs.create`; a folder id, an unknown id and a foreign-profile id all fail closed with a terminal `.catch(() => {})` |

| T-11-05 | Tampering | managed / root bookmark | mitigate | `bm.unstar` skips nodes marked `unmodifiable`; `bm.remove` relies on Chrome's modify-managed and modify-special rejections, each swallowed per-node so one rejection cannot abort the batch |
| T-11-06 | Tampering | unstar blast radius | mitigate | Raw exact string equality against `tab.url` with zero normalization, asserted by the task-1 automated check; `search({url})` matches verbatim and cannot return folders, so unstar can never reach a folder |

| T-11-03 | Information Disclosure | `el.bookmarked` computation | mitigate | The URL set is module-local and never serialized; `extension_bm_elements_carry_no_url` guards the element shape at source level |
| T-11-01 | Information Disclosure | tri-state misreport | mitigate | `bmUrlSet === null` omits the key from every tab rather than emitting `false`, so an unreadable tree renders no star at all instead of a false negative |
| T-11-SC | Tampering | supply chain | mitigate | Zero packages added; the guard test uses `serde_json`, already a `server-core` dependency |
