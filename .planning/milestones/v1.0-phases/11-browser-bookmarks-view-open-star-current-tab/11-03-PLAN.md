**`codec/json.rs`** — add six payload structs beside the tabs ones, following the exact
`TabsListPayload`/`TabsChangedPayload` attribute style (`#[serde(default, skip_serializing_if = "Option::is_none")]`
on every `Option`):

- `BmListPayload` — the dual request/reply shape, ALL fields optional so a bare `{}` request
  decodes: `connected: Option<bool>`, `nodes: Option<Vec<BmNode>>`, `truncated: Option<bool>`.
  Doc-comment it exactly as `TabsListPayload` is: request is `{}` (all fields absent); the reply
  carries `connected` and `nodes`.
- `BmChangedPayload` — the S-to-C push: `connected: bool` and `nodes: Vec<BmNode>` are REQUIRED (a
  missing field is a hard decode error, unlike the dual `bm.list`); `truncated: Option<bool>` is
  the additive optional.
- `BmOpenPayload` — `node_id: String` with `#[serde(rename = "nodeId")]`.
- `BmStarPayload` — `tab_id: i64` with `#[serde(rename = "tabId")]`.
- `BmUnstarPayload` — `tab_id: i64` with `#[serde(rename = "tabId")]`.
- `BmRemovePayload` — `node_id: String` with `#[serde(rename = "nodeId")]`.

Doc-comment the `nodeId`/`tabId` split explicitly on `BmOpenPayload`: Chrome bookmark ids are
strings and tab ids are integers; reusing the key name `id` for both would decode fine under the
value-lenient codec and fail silently inside the extension, so the two id kinds are named apart
and the Rust types (`String` vs `i64`) are the enforcement.

Then add `BmList(BmListPayload)`, `BmChanged(BmChangedPayload)`, `BmOpen(BmOpenPayload)`,
`BmStar(BmStarPayload)`, `BmUnstar(BmUnstarPayload)`, `BmRemove(BmRemovePayload)` to the `Msg`
enum after the tabs variants, the six `"bm.list" => Msg::BmList(payload(p)?)`-style decode arms
after the tabs decode arms, and the six `Msg::BmList(pl) => ("bm.list", val(pl))`-style encode
arms after the tabs encode arms.

**`dispatch/router.rs`** — add, immediately after the tabs block:

- The READ arm: `Msg::BmList(_)` calls `exec.bookmarks.list()` and replies with a single
  `Msg::BmList(BmListPayload { connected: Some(state.connected), nodes: Some(state.nodes),

  `Msg::BmUnstar(p)` calls `exec.bookmarks.unstar(p.tab_id)`; `Msg::BmRemove(p)` calls
  `exec.bookmarks.remove(&p.node_id)`. Comment that no err reply exists for any of them (SPEC

- `Msg::BmChanged(_)` — add to the S-to-C-only silently-ignored group next to `Msg::TabsChanged(_)`.
  It must NOT produce an `unknownType` err: the type IS known, only the direction is wrong.

Add no new `err` codes anywhere.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authed phone → router | `nodeId` / `tabId` values from the phone are untrusted input crossing into executor calls |
| router → phone (bm.list reply) | Bookmark titles leave the machine here |
| paused state → executor | The pause gate is the "phone must not change the PC" boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-09 | Elevation of Privilege | `bm.*` routing | mitigate | `router::route` is structurally unreachable before `AuthState::Authed` (SPEC section 6, session.rs); the four commands are additionally added to `is_executor_bound` so the pause gate drops them, proven by the extended paused-drop test |
| T-11-05 | Tampering | `bm.remove` on a managed/root node | transfer | The router passes the opaque `nodeId` through without interpretation; Chrome rejects `kModifySpecialError`/`kModifyManagedError` and the extension swallows it (11-06). The phone hides the affordance via the `locked` flag |
| T-11-10 | Tampering | `nodeId`/`tabId` type confusion | mitigate | Distinct wire key names with distinct Rust types (`String` vs `i64`) make a swap a hard decode error, pinned by fixtures `03`-`06` and `08`, and by the task-3 pass-through test |
| T-11-02 | Information Disclosure | router err strings | mitigate | This plan adds NO new err codes and NO err strings; the family is fire-and-forget (SPEC section 7). No log line carries a node title |
| T-11-06 | Tampering | `bm.unstar` blast radius | transfer | The server never sees a URL; exact-URL matching and the delete loop live entirely in the extension (11-06), and the confirm gate lives in the client (11-10/11-11) |
| T-11-SC | Tampering | supply chain | mitigate | Zero new crates; `Cargo.toml` is not in `files_modified` |
</threat_model>
