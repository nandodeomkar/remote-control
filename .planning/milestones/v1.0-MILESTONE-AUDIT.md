# Milestone v1.0 — Audit

**Status: `gaps_found`** — one genuine product gap (CONN-04), no blockers, and a
substantial pile of documentation drift that is worth clearing before archival.

This audit deliberately checks **delivered outcomes against original intent**, not
file counts. STATE.md records why: for eight weeks the progress counter read 100%
while `12-18-SUMMARY.md` carried `## Self-Check: FAILED`. **A SUMMARY on disk is not
an outcome** — and, as this audit found, the converse is also true: a pessimistic
artifact on disk is not a failure either.

## The one real gap

### CONN-04 — IP-change recovery is screen-scoped

> "Connection recovers automatically after WiFi drops or PC IP changes (backoff +
> beacon re-listen)"

The WiFi-drop half works. The **IP-change half is conditionally unreachable.**

`ConnectionService.attachBeacons` ([connection_service.dart:765](app/remote_control/lib/net/connection_service.dart:765))
is called from exactly one place — [device_list_store.dart:272](app/remote_control/lib/store/device_list_store.dart:272),
inside `DeviceListNotifier.build()`. That notifier only builds when
`deviceListProvider` is watched, which happens in the device-list screen and in
Settings. **`hub_screen.dart` watches neither.**

So on a cold start that lands on the hub and never visits Settings or the device
list, `main.dart:73-92` dials the *stored* host, and the D-06 beacon short-circuit
that rewrites host/port ([reconnect_fsm.dart:281-295](app/remote_control/lib/net/reconnect_fsm.dart:281))
can never fire — the client retries a stale address indefinitely after the router
hands the PC a new IP.

**Why it is a WARNING and not a blocker:** opening Settings or the device list even
once brings the listener up for the whole process lifetime (Riverpod 3
`NotifierProvider` is keep-alive), and manual IP entry (CONN-05) is a discoverable
recovery path. This is a first-run / never-opened-Settings window, not a permanent
break.

**Fix shape:** one line, no new machinery — have `connectionServiceProvider` (or
`main.dart`'s init) own a `BeaconListener` and call `attachBeacons`, instead of
leaving that to a screen-scoped provider.

## Verdict

The system is **genuinely integrated, not a set of silos**. The language boundary is
machine-enforced against one shared fixture tree with both suites passing; the
executor seam has no dangling methods in either direction; the keymap is byte-identical;
and both double-mounted surfaces really do share one engine.

v1.0 delivered what it set out to deliver. What it did not do is finish writing that
down — four missing verification documents, one stale one, and five stale requirement
entries. That is worth an hour before archival, because v1.1 is about to build
directly on phases 8 and 10.
